# 설계 결정사항

> 이 문서는 2026-07-30 기준 확정 또는 준확정된 프로젝트 방향을 정리한다. 구현 중 바뀌는 내용은 각 기능 명세와 함께 갱신한다.

## 1. 프로젝트 범위

- 서비스명: 감자나라
- 주 기능: 중고거래, 경매, 채팅, 알림, 마이페이지, 관리자
- 문서화 목표: 기능 명세, 전체 플로우, API, Socket 이벤트, 서버 아키텍처, Mermaid 다이어그램, 구현 체크리스트
- 설계 기간: 2026-07-29 ~ 2026-08-02
- 구현/브랜치/병합/동작 목표: 2026-08-09

## 2. 서버 기술 스택

- Runtime: Node.js
- Server: Express
- DB: PostgreSQL
- Cache/Realtime State: Redis
- Realtime: Socket.IO
- Scheduler: 경매별 종료 Timer + 복구용 Scheduler
- Upload: multer 기반 local `uploads/`, 공개 URL prefix `/resources`
- 배포: `.env` 기반 환경변수 분리, Docker Compose 적용 가능 구조 지향

## 3. 후순위 확장 항목

- S3 또는 S3-compatible object storage
- Load Balancer
- Socket.IO Redis adapter
- Redis Stream + Worker 기반 비동기 입찰 저장
- TypeScript 전환
- 고급 통계 대시보드

## 4. 인증 정책

- Access Token과 Refresh Token은 모두 HttpOnly 쿠키로 전달한다.
- Access Token 만료 시간은 15분이다.
- Refresh Token 만료 시간은 7일이다.
- Access Token 쿠키 path는 `/`로 둔다.
- Refresh Token 쿠키 path는 `/api/auth/refresh`로 둔다.
- Refresh Token Rotation을 적용한다.
- 여러 기기 로그인은 허용한다. 각 기기/브라우저 세션은 별도 refresh session을 가진다.
- Access Token claim은 `sub`, `sid`, `jti`, `type=access`, `role`, `iat`, `exp`를 사용한다.
- Refresh Token claim은 `sub`, `sid`, `jti`, `type=refresh`, `iat`, `exp`를 사용한다.
- Redis refresh session key 형식은 `session:{sub}:{sid}`로 통일한다.
- 로그아웃 시 현재 브라우저 세션의 refresh key만 삭제하고 access/refresh 쿠키를 만료시킨다.
- 회원 탈퇴와 관리자 영구정지는 해당 사용자의 모든 refresh session을 삭제한다.
- 정지/탈퇴 사용자는 로그인, 토큰 재발급, 보호 API, Socket 연결을 차단한다.
- 회원가입 성공 후 자동 로그인하지 않는다. 사용자가 로그인 API를 다시 호출해야 토큰을 발급한다.

## 5. 전화번호 인증 정책

- 전화번호 인증은 `purpose`로 구분한다.
- 사용 purpose: `SIGNUP`, `FIND_ID`, `RESET_PASSWORD`, `CHANGE_PHONE`
- 인증번호 TTL은 3분이다.
- 재발송 cooldown은 30초이다.
- 인증 완료 세션 TTL은 10분이다.
- 회원가입 성공, 아이디 찾기 성공, 비밀번호 재설정 성공, 전화번호 변경 성공 시 인증 완료 세션을 소비한다.
- 회원가입 전화번호는 10분 동안 Redis reservation key로 임시 선점한다.
- 같은 전화번호/이메일은 정지 또는 탈퇴 이후에도 재사용할 수 없다.

## 6. Redis 사용 정책

- Refresh Token session 관리
- 전화번호 인증번호, cooldown, 인증 완료 세션, 회원가입 전화번호 reservation 관리
- 경매 현재 최고 입찰 상태 관리
- Redis 장애 시 신규 입찰은 차단한다.
- Redis 상태는 PostgreSQL 기준으로 복원 가능해야 한다.
- 최종 영속 데이터 기준은 PostgreSQL이다.

## 7. 중고거래/경매 삭제 정책

- 중고글과 경매글은 취소 상태를 사용하지 않는다.
- 사용자는 본인이 작성한 중고글/경매글을 수정할 수 있다.
- 사용자는 본인이 작성한 중고글/경매글을 삭제할 수 있다.
- 관리자는 중고글/경매글을 삭제할 수 있다.
- 삭제는 물리 삭제가 아니라 `listings.deleted_at`, `deleted_by`, `delete_reason`으로 처리한다.
- 삭제된 글은 검색, 목록, 관심목록, 마이페이지, 외부 프로필 등 일반 사용자 화면에서 조회되지 않는다.
- 삭제된 글 상세 URL에 직접 접근하면 존재하지 않는 글처럼 `404 NOT_FOUND`를 반환한다.
- 삭제 시 해당 글의 `favorites` 행은 삭제한다.
- 삭제된 글과 연결된 입찰, 거래, 채팅, 후기 이력은 DB에서 보존한다.
- 완료된 거래내역에서는 과거 상품 snapshot 정보를 보여주되, 삭제된 글의 상세 이동은 비활성화한다.

## 8. 경매 정책

- 경매 등록 시 기본 종료 시간은 시작 시각 기준 24시간이다.
- 경매 생성 시 경매별 종료 Timer를 등록한다.
- 서버 시작 시 진행 중 경매 Timer를 복원한다.
- Timer 누락 또는 서버 장애를 대비해 복구용 Scheduler가 종료 누락 경매를 확인한다.
- 경매 현재가와 최고 입찰자는 Redis에서 빠르게 확인한다.
- 입찰 비교와 최고 입찰자 갱신은 Redis Lua script 또는 동등한 원자 처리로 보장한다.
- 입찰 성공 시 PostgreSQL에도 입찰 내역을 저장한다.
- 경매 종료 시 `auction_posts.status = FINISHED`로 변경한다.
- 종료된 경매는 삭제되지 않았다면 검색, 마이페이지, 외부 프로필에서 조회 가능하다.
- 종료된 경매는 입찰과 채팅이 비활성화된다.
- 종료된 경매에도 관심 추가는 가능하다.
- 종료된 경매도 작성자 또는 관리자가 삭제할 수 있다.
- 진행 중 경매도 soft delete할 수 있다.
- 진행 중 경매가 삭제되면 기존 입찰자에게 `LISTING_DELETED` 알림을 사용자당 1회 저장한다.
- 진행 중 경매가 삭제되면 경매 Timer를 제거하고 Redis 경매 상태/참여자 정보를 제거한다.
- 진행 중 경매가 삭제되면 경매 Socket Room에 `auction:deleted`를 전송한다.
- 삭제된 경매는 Timer 복원과 Recovery Scheduler 대상에서 제외한다.
- 진행 중 경매의 최고 입찰자가 탈퇴/정지되면 다음 유효 입찰자로 최고 입찰자를 재계산한다.
- 다음 유효 입찰자가 없으면 최고 입찰자를 `NULL`로 두고 현재가를 시작가로 복원한다.
- 최고 입찰자 재계산 시 기존 입찰 기록은 삭제하지 않는다.
- 최고 입찰자 재계산 결과는 `auction:leader-changed`로 전송하고, 내부 제재 사유는 사용자에게 노출하지 않는다.

## 9. 거래/송금 요청 정책

- 채팅방에서 판매자만 송금 요청을 생성할 수 있다.
- 판매자가 송금 요청을 생성하면 `transactions.status = REQUESTED` 행이 생성된다.
- 구매자는 채팅방의 송금 요청 링크를 눌러 송금 페이지로 이동한다.
- 구매자가 송금하면 `transactions.status = COMPLETED`가 된다.
- 판매자가 송금 요청을 취소하면 `transactions.status = CANCELED`가 된다.
- 거래 참여자가 탈퇴하거나 영구정지되면 진행 중인 `REQUESTED` 거래를 `CANCELED`로 변경한다.
- 판매자는 같은 상품과 같은 구매 희망자에게 활성 송금 요청을 2개 이상 만들 수 없다.
- 삭제/정지/탈퇴 사용자에게 새로운 송금 요청을 생성할 수 없다.
- 송금 요청 취소 시 별도 취소 사유와 취소 시각 컬럼은 두지 않는다. 취소 여부는 `status`, 변경 시각은 `updated_at`으로 판단한다.
- 게시글/경매의 취소 상태와 거래 요청 취소 상태는 서로 다른 개념이다.

## 10. 관리자 정책

- 관리자 UI의 "회원 삭제"는 내부적으로 사용자 영구정지다.
- 실제 사용자 row를 물리 삭제하지 않는다.
- `users.banned_at IS NOT NULL`이면 영구정지 사용자로 본다.
- `banned_until`은 DB에 유지하지만 MVP에서 사용하지 않는다.
- 정지된 사용자의 login_id, phone, email은 계속 보존하며 재사용할 수 없다.
- 정지/탈퇴 사용자는 일반 사용자 화면에서 닉네임을 `삭제된 사용자`로 표시한다.
- 정지/탈퇴 사용자의 프로필 이미지와 프로필 이동은 비활성화한다.
- 정지/탈퇴 사용자와의 기존 거래, 후기, 채팅 기록은 보존한다.
- 정지/탈퇴 사용자가 포함된 기존 채팅방은 읽기 전용으로 유지한다.
- 관리자는 게시물/경매글을 삭제할 수 있다.
- 관리자는 회원별 관리자 메모를 저장할 수 있다.

## 11. 회원 정보 수정 정책

- 회원 정보 수정 화면 진입 전 현재 비밀번호 확인을 거친다.
- 회원 정보 수정에서 닉네임, 이메일, 비밀번호, 전화번호를 변경할 수 있다.
- 전화번호 변경은 새 전화번호 인증을 완료해야 저장할 수 있다.
- 비밀번호 변경은 새 비밀번호와 새 비밀번호 확인 일치, 비밀번호 규칙 검증을 거친다.
- 닉네임과 이메일은 중복/형식 검증을 거친다.
- 회원 탈퇴 버튼은 항상 노출하되 재확인 절차를 거친다.

## 12. 후기 정책

- 거래가 완료된 뒤 구매자와 판매자 모두 서로에게 후기를 작성할 수 있다.
- 한 거래에서 같은 사용자는 한 번만 후기를 작성할 수 있다.
- 평점은 1~10 DB 값으로 저장하되 UI에서는 0.5 단위 별점 표현을 사용할 수 있다.

## 13. 알림 정책

- 일반 알림은 DB `notifications`에 먼저 저장한다.
- 사용자가 Socket.IO에 접속 중이면 실시간 이벤트도 함께 보낸다.
- 사용자가 접속 중이지 않으면 DB의 `is_read=false` 상태로 남긴다.
- 채팅 메시지 알림은 수신자가 해당 채팅방을 보고 있지 않을 때만 DB에 저장한다.
- 수신자가 해당 채팅방을 보고 있으면 `NEW_MESSAGE` 알림 row를 만들지 않고 Socket 이벤트와 unread count 갱신만 처리한다.
- 저장된 채팅 메시지 알림은 알림 목록에서 채팅방별 집계가 가능해야 한다.
- 알림 unread count는 증감값이 아니라 절대값으로 전송한다.

## 14. 사용자 비활성화 공통 처리

관리자 영구정지와 사용자 자진 탈퇴는 공통 비활성화 서비스를 통해 처리한다.

- 모든 refresh session 삭제
- Socket 연결 강제 종료
- 진행 중인 `REQUESTED` 거래를 `CANCELED`로 변경
- 소유한 진행 중 경매 soft delete
- 최고 입찰 중인 진행 중 경매 재계산
- 관련 Redis 상태 정리
- 관련 Timer 정리
- 필요한 알림 저장 및 Socket 이벤트 전송

## 15. 파일 업로드 정책

- 범용 `/api/uploads/images` API는 사용하지 않는다.
- 프로필 이미지와 게시글 이미지는 각각의 도메인 요청에서 `multipart/form-data`로 처리한다.
- 물리 저장은 multer local `uploads/`를 사용한다.
- 공개 정적 URL prefix는 `/resources`를 사용한다.
- DB에는 `profile_image`, `post_images.image_url` 문자열을 저장한다.
- S3 전환을 고려해 storage service 계층을 둔다.

## 16. 서버 구조 보완 원칙

- DB 변경 이력은 추후 `database/migrations/`에 SQL 파일로 관리할 수 있다.
- 개발용 초기 데이터는 추후 `database/seeds/`에 분리할 수 있다.
- 알림 저장과 Socket 전송은 `notification.emitter.js` 같은 전용 모듈로 분리하는 것을 권장한다.
- Redis Stream Worker는 MVP 구현 범위가 아니라 확장 항목이다.
- 이번 문서 범위에 테스트 구조는 포함하지 않는다.

## 17. 문서 작성 원칙

- 기능 명세는 용어를 풀어쓴다.
- 명세 수준은 낮추지 않는다.
- 미확정 내용은 임의 확정하지 않고 `미결정 정책.md`에 모은다.
- 개발자가 바로 체크할 수 있도록 각 문서에 체크리스트를 둔다.
