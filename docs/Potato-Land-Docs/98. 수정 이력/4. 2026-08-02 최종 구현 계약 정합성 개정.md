# 2026-08-02 최종 구현 계약 정합성 개정

## 인증과 전화번호

- refresh 성공 시 Access Token과 Refresh Token을 함께 rotation한다.
- refresh session `session:{sub}:{sid}`의 jti 검증은 refresh와 logout에서만 수행한다.
- logout 경로를 refresh cookie path 안의 `POST /api/auth/refresh/logout`으로 고정했다.
- 전화번호 발송 시 서버가 `phoneVerificationId`를 만들고 Redis code/verified value에 저장한다.
- verify, status, 회원가입, 아이디 찾기, 비밀번호 재설정, 전화번호 변경은 같은 식별자를 제출·검증한다.
- 전화번호 인증 완료 상태는 최종 목적 API 성공 뒤 소비하며 DELETE status API는 제거했다.
- 회원가입 동의값은 단일 체크박스와 `termsAgreed` 하나로 통일했다.
- 아이디만 전용 사전 중복 API를 사용하고 닉네임·선택 이메일은 signup 서비스와 DB UNIQUE로 최종 검증한다.

## 채팅 읽음

- `chat_room_reads`, `lastReadMessageIdx`, `chat:read:updated`를 사용하지 않는다.
- 채팅방 입장 또는 `chat:read { chatRoomIdx }`는 `notifications`와 `chat_messages`를 join해 그 방의 저장된 `NEW_MESSAGE` 알림을 모두 읽음 처리한다.
- unread count는 `notifications.is_read=false`를 기준으로 계산한다.
- 수신자의 연결 중 하나라도 해당 채팅방을 보는 중이면 `NEW_MESSAGE` row를 만들지 않는다.
- 메시지별 스크롤 위치와 상대방 읽음 확인은 MVP 범위가 아니다.

## DB와 비활성 사용자

- 한 listing에는 `REQUESTED` 또는 `COMPLETED` transaction이 합쳐서 최대 1개만 존재한다. `CANCELED` 이력은 여러 건 허용한다.
- 서버가 만든 `SYSTEM`, `TRADE_COMPLETE` 메시지는 `sender_idx=NULL`; 사용자 전송 타입은 sender가 필수다.
- 탈퇴·영구정지 사용자의 판매 중 중고글과 진행 중 경매를 soft delete하고 favorites를 제거한다.
- 기존 거래·채팅·후기·메시지는 보존한다.
- 실제 REQUESTED 거래가 CANCELED로 바뀔 때만 활성 상대방에게 일반 `PAYMENT_CANCELED`를 만들며, 요청이 없으면 알림도 없다.

## 알림

- `notificationType`은 발생 이벤트, `referenceType`은 이동할 참조 도메인으로 정의했다.
- 모든 타입의 reference, referenceIdx, 수신자, 생성 조건을 도메인 상태 표에 고정했다.

## 경매

- 입찰은 선택한 Redis-first, DB-second 순서를 유지한다.
- 입찰 경로에 경매 row lock을 추가하지 않는다.
- Redis 성공 뒤 DB 실패의 Redis 복구는 이번 구현에서 보장하지 않고 reconciliation 후속 범위로 남긴다.
- Redis Lua가 승인만 직렬화하므로 동시에 승인된 요청의 DB commit이 역전될 수 있음을 현재 MVP 한계로 명시했다.
- 후속 무결성 후보는 경매별 lock, version 조건부 update, reconciliation/outbox다.
- 종료 Timer와 Recovery Scheduler의 대상·최종 판정은 Redis가 아니라 DB의 status, ends_at, deleted_at을 기준으로 한다.
- 최소 입찰 단위의 현재가 구간과 100만원 이상 1% 올림 공식을 고정했다.

## API 상태 집합

- 실제 사용 상태만 문서화한다: 중고 `ON_SALE`, `SOLD`; 경매 `ON_GOING`, `FINISHED`.
- 확장용 미사용 `RESERVED`, `READY`는 API 허용 상수에서 제거했다.
