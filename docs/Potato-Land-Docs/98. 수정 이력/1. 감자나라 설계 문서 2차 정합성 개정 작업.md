# 2. 공통 용어와 상태 분류

## 2.1 Command, Query, Event

문서의 용어 사전과 다이어그램 읽는 법에 다음 의미를 추가한다.

### Command

시스템의 상태를 바꿔 달라는 요청이다.

예:

- 회원가입
    
- 메시지 전송
    
- 입찰
    
- 거래 요청
    
- 거래 완료
    
- 알림 읽음 처리
    

HTTP 또는 Socket 중 어느 수단으로 전달되는지는 Command의 정의와 무관하다.

### Query

시스템 상태를 변경하지 않고 데이터를 조회하는 요청이다.

예:

- 상품 목록 조회
    
- 채팅 메시지 조회
    
- 알림 목록 조회
    

### Event

이미 성공적으로 발생한 사실을 다른 대상에게 전파하는 것이다.

예:

- 메시지가 저장됨
    
- 현재 입찰가가 갱신됨
    
- 경매가 종료됨
    
- 새 알림이 생성됨
    

중요한 상태 변경은 DB 또는 Redis 처리가 성공한 다음 이벤트로 전파한다.

## 2.2 영속 도메인 상태

다음 상태는 PostgreSQL이 최종 기준이다.

### 사용자

사용자 상태는 별도 enum 컬럼이 아니라 다음 조건으로 해석한다.

- 정상: `deleted_at IS NULL AND banned_at IS NULL`
    
- 영구정지: `banned_at IS NOT NULL`
    
- 탈퇴: `deleted_at IS NOT NULL`
    

우선순위는 영구정지와 탈퇴가 동시에 설정되지 않도록 Service에서 제한한다.

`role`은 상태가 아니라 권한 분류다.

- `USER`
    
- `ADMIN`
    

비회원 `GUEST`는 DB의 `user_role`에 저장하지 않고 프론트 및 인증 컨텍스트에서만 사용하는 가상 역할이다.

### 중고거래

- `ON_SALE`
    
- `SOLD`
    
- `CANCELED`
    

허용 전이:

- `ON_SALE -> SOLD`
    
- `ON_SALE -> CANCELED`
    

`SOLD`, `CANCELED`에서는 수정, 거래 요청, 관심 추가, 신규 채팅 등 상태 변경 행위를 제한한다.

### 경매

- `ON_GOING`
    
- `FINISHED`
    
- `CANCELED`
    

허용 전이:

- `ON_GOING -> FINISHED`
    
- `ON_GOING -> CANCELED`
    

판매자가 직접 경매를 수정하거나 취소하는 기능은 없다.

### 거래

- `REQUESTED`
    
- `COMPLETED`
    
- `CANCELED`
    

`transaction_type`은 상태가 아니라 거래 종류다.

- `DIRECT_SALE`
    
- `AUCTION`
    

허용 전이:

- `REQUESTED -> COMPLETED`
    
- `REQUESTED -> CANCELED`
    

`COMPLETED`, `CANCELED`는 최종 상태다.

### 알림

- `is_read=false`
    
- `is_read=true`
    

이번 MVP에서는 `read_at` 컬럼을 새로 추가하지 않는다.

### 카테고리

- `is_active=true`
    
- `is_active=false`
    

일반 사용자용 카테고리 API는 활성 카테고리만 반환한다.

## 2.3 런타임 상태

다음 상태는 PostgreSQL의 영속 도메인 상태와 구분한다.

- Socket 연결 여부
    
- Socket이 가입한 사용자 Room
    
- 현재 보고 있는 채팅 Room
    
- 현재 보고 있는 경매 Room
    
- 전화번호 인증번호
    
- 전화번호 인증 발송 대기 상태
    
- 전화번호 인증 완료 세션
    
- 회원가입 전화번호 임시 선점
    
- Redis 경매 현재가
    
- Redis 경매 최고 입찰자
    
- 경매 종료 타이머
    
- Worker 처리 중인 작업
    

## 2.4 운영 상태

다음은 비즈니스 상태가 아니라 시스템 운영 상태다.

- PostgreSQL 연결 정상 여부
    
- Redis 연결 정상 여부
    
- Socket.IO 서버 정상 여부
    
- 경매 Scheduler 정상 여부
    
- Worker 정상 여부
    
- SMS 서비스 정상 여부
    

이 상태는 DB 비즈니스 테이블이 아니라 다음으로 관찰한다.

- health check
    
- structured log
    
- heartbeat
    
- process monitoring
    
- Docker healthcheck

# 3. 인증과 사용자 정책

## 3.1 쿠키 정책

Access Token과 Refresh Token은 HttpOnly 쿠키로 전달한다.

### Access Token

- 쿠키 이름 예시: `access_token`
    
- 만료: 15분
    
- Path: `/api`
    
- HttpOnly: true
    
- SameSite: `Lax`
    
- 운영 환경 Secure: true
    

### Refresh Token

- 쿠키 이름 예시: `refresh_token`
    
- 만료: 7일
    
- Path: `/api/auth`
    
- HttpOnly: true
    
- SameSite: `Lax`
    
- 운영 환경 Secure: true
    

Refresh 쿠키 Path를 `/api/auth/refresh`로 제한하지 않는다. 로그아웃 API에서도 Refresh Token을 확인해 현재 세션의 Redis key를 삭제해야 하기 때문이다.

### 전화번호 인증 세션 쿠키

- 쿠키 이름 예시: `phone_verification`
    
- HttpOnly: true
    
- Path: `/api`
    
- TTL: 10분
    
- Redis의 인증 완료 식별자를 보관한다.
    

## 3.2 JWT claim

JWT claim에는 최소한 다음을 둔다.

- `sub`: 사용자 idx
    
- `role`: `USER` 또는 `ADMIN`
    
- `jti`: 토큰 고유 식별자
    
- `iat`
    
- `exp`
    

여러 기기 로그인 세션을 구체적으로 분리할 때에는 `sessionId` 또는 `sid` claim을 추가할 수 있도록 문서에 확장 지점을 남긴다.

## 3.3 Refresh Token Rotation

이번 문서에서는 Refresh Token Rotation을 적용하는 것으로 통일한다.

성공적인 Refresh 시:

1. 기존 Refresh Token을 검증한다.
    
2. Redis에 저장된 세션과 일치하는지 확인한다.
    
3. 기존 Refresh Token을 폐기한다.
    
4. 새 Access Token과 새 Refresh Token을 발급한다.
    
5. Redis TTL을 7일로 갱신한다.
    

여러 기기 로그인은 허용한다. 기기 또는 브라우저 세션마다 별도의 Refresh 세션을 가진다.

Redis key 예시는 다음 형태로 통일한다.

```text
auth:refresh:{userIdx}:{sessionId}
```

값에는 원본 Refresh Token을 그대로 저장하지 말고 다음 정보를 저장하는 방향으로 작성한다.

- Refresh Token hash
    
- 현재 Refresh Token jti
    
- 생성 시각
    
- 필요하면 user agent 등 보조 정보
    

로그아웃은 현재 브라우저 세션의 Redis key만 삭제한다.

관리자 영구정지와 회원 탈퇴는 해당 사용자의 모든 Refresh 세션을 삭제한다.

## 3.4 로그인 ID 보존

영구정지 또는 회원 탈퇴 시 `login_id`를 삭제하거나 NULL로 만들지 않는다.

다음 정보를 모두 보존한다.

- login_id
    
- phone
    
- email
    
- 기존 게시글
    
- 거래
    
- 채팅
    
- 후기
    
- 입찰 내역
    

접근 가능 여부는 `banned_at`, `deleted_at`으로 판단한다.

### 영구정지

- 로그인 차단
    
- Refresh 차단
    
- 보호 API 차단
    
- Socket 강제 연결 종료
    
- Redis Refresh 세션 전체 삭제
    
- 진행 중 중고거래 글 자동 취소
    
- 진행 중 경매 자동 취소
    
- 정지 안내 SMS 전송
    
- 공개 프로필 접근 차단
    
- 재회원가입 차단
    

정지 사유가 입력되지 않으면 기본값:

```text
관리자에 의해 정지되었습니다.
```

사용자에게 보내는 경매 취소 알림에는 정지 사실이나 정지 사유를 노출하지 않는다.

### 회원 탈퇴

- `deleted_at` 설정
    
- 로그인 차단
    
- Refresh 차단
    
- 보호 API 차단
    
- Socket 강제 연결 종료
    
- Redis Refresh 세션 전체 삭제
    
- 공개 프로필 접근 차단
    

MVP에서는 탈퇴 계정의 로그인과 동일 전화번호 재가입을 허용하지 않는 것으로 문서를 통일한다. 계정 복구 기능은 범위 밖이다.

## 3.5 CSRF 정책

쿠키로 인증하므로 CSRF 위험을 문서에 포함한다.

MVP의 기본 전제:

- 프론트와 API는 동일 사이트 배포
    
- `SameSite=Lax`
    
- 허용 Origin을 정확하게 지정한 CORS
    
- `credentials=true`
    
- GET 요청에서 상태를 변경하지 않음
    
- 상태 변경은 POST/PATCH/DELETE 사용
    

프론트와 API가 실제 교차 사이트로 분리되어 `SameSite=None`이 필요해지는 경우에는 CSRF Token 방식을 추가해야 한다고 확장 정책에 기록한다.

## 3.6 bcrypt

고정 salt 문자열을 환경변수에 저장하지 않는다.

bcrypt가 비밀번호마다 salt를 자동 생성하게 하고, 환경변수에는 cost 값만 둔다.

```text
BCRYPT_SALT_ROUNDS=12
```

# 4. 전화번호 인증 정책

## 4.1 인증 목적

전화번호 인증 로직은 공통 서비스로 작성하고 다음 `purpose`로 구분한다.

- `SIGNUP`
    
- `FIND_ID`
    
- `RESET_PASSWORD`
    
- `CHANGE_PHONE`
    

`CHANGE_PASSWORD`는 현재 기준에서 사용하지 않는다. 비밀번호 변경은 내 정보 수정 전 비밀번호 확인으로 발급받은 `verificationToken`을 사용한다.

발송 요청과 검증 요청 body에는 항상 `purpose`가 포함되고, 응답에도 `purpose`를 반환한다.

## 4.2 Redis key

다음 key naming 규칙을 문서에 추가한다.

```text
phone:code:{phone}:{purpose}
phone:cooldown:{phone}:{purpose}
phone:verified:{phone}:{purpose}
회원가입 전화번호 reservation key(현재 정책에서는 폐기)
```

### 인증번호

- TTL: 180초
    
- 6자리 숫자
    
- 원본 인증번호 저장 여부는 구현 단계에서 hash 저장을 우선 검토
    
- 재발송 대기: 30초
    

### 재발송 대기

```text
phone:cooldown:{phone}:{purpose}
```

- TTL: 30초
    
- key가 존재하면 재발송 거부
    

### 인증 완료 세션

```text
phone:verified:{phone}:{purpose}
```

값 예시:

```json
{
  "purpose": "SIGNUP",
  "phone": "01012345678",
  "userIdx": null
}
```

- TTL: 600초
    
- 검증 성공 시 생성
    
- 별도 verificationId를 발급하지 않고 `phone + purpose` 기준으로 확인
    
- 회원가입, 아이디 찾기, 비밀번호 재설정, 전화번호 변경이 성공하면 즉시 소비하여 삭제
    
- 만료되면 자동 삭제
    

### 회원가입 전화번호 선점

사용자가 `SIGNUP` 인증을 성공한 뒤 10분 동안 다른 인증 세션이 같은 전화번호를 회원가입용으로 선점하지 못하게 한다.

```text
SIGNUP reservation key(현재 정책에서는 폐기)
```

값:

```text
reserved
```

- `SET NX`
    
- TTL: 600초
    
- 같은 전화번호와 목적의 회원가입 재시도는 TTL 안에서 허용
    
- 회원가입 성공 시 삭제
    
- 회원가입 최종 무결성은 DB의 `UNIQUE(phone)`가 보장
    

## 4.3 목적별 검증

### SIGNUP

인증번호 발송 전에 DB의 전화번호 중복을 확인한다.

정상, 정지, 탈퇴 계정 어느 쪽이든 같은 전화번호가 존재하면 신규 회원가입을 거부한다.

### FIND_ID

- 정상 계정만 허용
    
- 정지 계정이면 정지 사용자 오류
    
- 탈퇴 또는 미존재 계정이면 일치 계정 없음
    
- 검증 성공 후 웹 응답에 아이디를 직접 노출하지 않고 SMS로 login_id 전송
    
- API 응답은 성공 여부만 반환
    

### RESET_PASSWORD

- 정상 계정만 허용
    
- 인증 완료 후 새 비밀번호를 설정
    
- 기존 비밀번호를 반환하거나 임시 비밀번호를 발급하지 않음
    
- 성공 후 해당 사용자의 기존 Refresh 세션 전체 삭제
    

### CHANGE_PHONE

- 로그인 사용자만 허용
    
- 변경하려는 새 전화번호가 기존 사용자 전화번호와 중복되지 않아야 함
    
- 인증 완료 후 내 정보 수정 API에서 새 전화번호로 변경
    
- 성공 후 `phone:verified:{phone}:CHANGE_PHONE`을 소비
    

## 4.4 인증 시도 횟수

이번 MVP에서는 인증번호 검증 횟수 제한을 구현하지 않는 결정으로 기록한다.

단, 보안상 위험과 다음 확장 항목을 명시한다.

- 인증번호별 최대 검증 횟수
    
- 전화번호별 rate limit
    
- IP별 rate limit
    
- 실패 횟수 Redis key
    

이를 미결정 정책이 아니라 “MVP 제외 보안 고도화 항목”으로 분류한다.

# 5. API 공통 규칙

## 5.1 응답

성공:

```json
{
  "success": true,
  "data": {}
}
```

실패:

```json

  "success": false,

  "message": "사용자에게 표시할 수 있는 메시지"
}
```

## 5.2 인증 표기

기존 `optional` 표현을 다음으로 구체화한다.

- `PUBLIC`: 인증 정보를 사용하지 않는 공개 API
    
- `OPTIONAL_USER`: 비회원도 가능하지만 로그인 시 개인화 필드를 제공
    
- `USER`: 로그인 필수
    
- `ADMIN`: 관리자 필수
    
- `PARTICIPANT`: 관련 거래·채팅 참여자
    
- `SELLER`: 해당 상품 판매자
    
- `BUYER`: 해당 거래 구매자
    

## 5.3 일반 페이지네이션

일반 목록은 다음 규격을 사용한다.

- `page`: 1부터 시작
    
- `size`: 기본 10
    
- 최대 size: 50
    

응답:

```json
{
  "success": true,
  "data": {
    "items": [],
    "page": 1,
    "size": 10,
    "totalElements": 0,
    "totalPages": 0,
    "hasNext": false
  }
}
```

## 5.4 채팅 메시지 커서 페이지네이션

채팅 메시지는 처음부터 커서 방식으로 작성한다.

첫 요청:

```http
GET /api/chats/:chatRoomIdx/messages?size=30
```

이전 메시지 요청:

```http
GET /api/chats/:chatRoomIdx/messages?beforeMessageIdx=150&size=30
```

- 기본 size: 30
    
- 최대 size: 50
    
- DB에서는 최신 메시지부터 제한 조회
    
- 클라이언트 응답의 `items`는 과거에서 최신 순서로 정렬
    
- `nextCursor`는 다음 조회의 `beforeMessageIdx`로 사용
    

응답:

```json
{
  "success": true,
  "data": {
    "items": [],
    "nextCursor": 120,
    "hasNext": true
  }
}
```

- 판매자

- 거래 상태

- 경매 또는 중고거래 구분

## 6.7 거래와 후기


거래 기능이 채팅 UI 안에 있어도 API 도메인은 `transactions`를 유지한다.

### 직접거래 요청

판매자만 생성 가능하다.

요청 예:

```json
{
  "chatRoomIdx": 10,
  "amount": 30000
}
```

서버가 채팅방과 상품을 통해 다음을 파생한다.

- listingIdx
    
- sellerIdx
    
- buyerIdx
    
- transactionType

- `transactions` INSERT
    
- `PAYMENT_REQUEST` 시스템 메시지 INSERT

- DB commit

알림 목록은 MVP에서 페이지네이션하지 않는다.

기본적으로 읽지 않은 알림만 반환한다.

일반 알림은 각각 표시하고, `NEW_MESSAGE` 알림은 같은 채팅방별로 묶어서 표시한다.

메시지 알림 표시 예:

- 1개: `새 메시지가 도착했습니다.`
    
- 2개 이상: `3개의 메시지가 도착했습니다.`
    
- UI 표시는 최대 `99+`
    

헤더 종 아이콘 숫자는 전체 읽지 않은 notification row 수의 절대값이며 프론트에서 99 초과를 `99+`로 표시한다.

최신 결정에 따라 전체 읽음 API를 유지한다. “반드시 하나씩만 눌러야 한다”는 이전 메모는 폐기한다.

## 6.10 범용 업로드 API

다음 API를 삭제한다.

```text
POST /api/uploads/images
```

이미지는 각 도메인 API에서 직접 받는다.

- 사용자 프로필: `PATCH /api/users/me`
    
- 중고거래: `POST/PATCH /api/used`
    
- 경매: `POST /api/auctions`
    
- 채팅 이미지: `POST /api/chats/:chatRoomIdx/messages/images`
    

내부적으로 공통 Storage Service를 재사용한다.

# 7. Socket Room 정책

## 7.1 연결

클라이언트는 로그인 후 Socket.IO에 연결한다.

Socket handshake는 Access Token 쿠키를 사용한다.

인증 실패 시 Socket.IO middleware에서 연결을 거부하고 클라이언트는 기본 `connect_error` 이벤트를 받는다.

사용자 정의 `connect:success`는 제거한다.

사용자 정의 범용 `error` 이벤트도 제거한다.

Socket.IO의 기본 이벤트를 사용한다.

- `connect`
    
- `connect_error`
    
- `disconnect`
    

Command 처리 실패는 ACK 규격으로 반환한다.

## 7.2 Room 종류

### Socket 자체 Room

Socket.IO가 `socket.id` Room을 자동 관리한다. 문서에서 내부 동작으로만 설명하고 애플리케이션 Room 정책에는 포함하지 않는다.

### 사용자 개인 Room

```text
user:{userIdx}
```

Socket 인증 성공 직후 가입한다.

용도:

- 새 채팅방
    
- 채팅방 요약 갱신
    
- 새 알림
    
- 안읽음 수
    
- OUTBID
    
- 낙찰
    
- 관리자 정지로 인한 세션 종료
    

동일 사용자의 여러 탭과 여러 기기 Socket이 모두 같은 사용자 Room에 들어간다.

### 채팅 Room

```text
chat:{chatRoomIdx}
```

현재 실제로 열어 보고 있는 채팅방에만 가입한다.

왼쪽 목록에 채팅방 5개가 표시된다고 5개 Room에 가입하지 않는다.

새 채팅방으로 전환할 때:

1. 기존 활성 채팅 Room leave
    
2. 참여자 검증
    
3. 새 채팅 Room join
    
4. `socket.data.activeChatRoomIdx` 갱신
    

### 경매 Room

```text
auction:{listingIdx}
```

현재 보고 있는 경매 상세 화면에 진입할 때 가입한다.

입찰한 모든 경매 Room에 영구적으로 남지 않는다.

경매 상세 화면에서 나갈 때 leave한다.

## 7.3 연결 해제

Socket 연결이 끊기면 Socket.IO가 가입했던 Room에서 자동 제거한다.

명시적 정책:

- 채팅 화면 전환: `chat:leave`
    
- 경매 화면 이탈: `auction:leave`
    
- 로그아웃: 클라이언트 `socket.disconnect()`
    
- 사용자 영구정지: 서버가 사용자 Room의 Socket 강제 disconnect
    
- 회원 탈퇴: 서버가 사용자 Room의 Socket 강제 disconnect
    
- 경매 종료: Socket 연결 자체를 끊지 않고 `auction:ended` 전송
    
- 경매 취소: Socket 연결 자체를 끊지 않고 `auction:canceled` 전송

# 9. 채팅 Socket 이벤트

## 9.1 Client -> Server

### `chat:join`

```json
{
  "chatRoomIdx": 10
}
```

처리:

1. Socket 인증 사용자 확인
    
2. 채팅방 존재 확인
    
3. 구매자 또는 판매자인지 확인
    
4. 기존 활성 채팅 Room leave
    
5. 새 Room join
    
6. ACK
    

### `chat:leave`

```json
{
  "chatRoomIdx": 10
}
```

### `chat:message:send`

텍스트 전용이다.

```json
{
  "clientMessageId": "client-generated-uuid",
  "chatRoomIdx": 10,
  "messageType": "TEXT",
  "content": "안녕하세요"
}
```

처리 순서:

1. 인증
    
2. 참여자 검증
    
3. 메시지 길이와 타입 검증
    
4. DB Transaction 시작
    
5. `chat_messages` INSERT
    
6. `chat_rooms.last_message_at` 갱신
    
7. 수신자 `NEW_MESSAGE` notification INSERT
    
8. DB commit
    
9. 발신 Socket ACK
    
10. 채팅 Room과 사용자 Room으로 이벤트 전파
    

발신자가 낙관적 UI 메시지를 실제 DB 메시지로 교체할 수 있도록 응답에 `clientMessageId`를 그대로 포함한다.

### `chat:read`

방향은 반드시 `Client -> Server`다.

```json
{
  "chatRoomIdx": 10,
  "lastMessageIdx": 150
}
```

처리:

1. 참여자 검증
    
2. `lastMessageIdx`가 해당 채팅방 메시지인지 검증
    
3. 수신자가 받은 `NEW_MESSAGE` 알림 중 `messageIdx <= lastMessageIdx`인 행을 `is_read=true`
    
4. 사용자 개인 Room에 채팅방 안읽음 0 또는 재계산 값 전파
    
5. 전체 알림 안읽음 수 절대값 전파
    
6. ACK
    

모든 messageIdx를 배열로 보내지 않는다.

## 9.2 Server -> Client

### `chat:message:new`

오른쪽 열린 채팅창을 갱신한다.

```json
{
  "chatRoomIdx": 10,
  "message": {
    "messageIdx": 150,
    "clientMessageId": "client-generated-uuid-or-null",
    "senderIdx": 2,
    "messageType": "TEXT",
    "content": "안녕하세요",
    "imageUrl": null,
    "transactionIdx": null,
    "createdAt": "2026-07-30T00:00:00.000Z"
  }
}
```

텍스트 Socket 명령에서는 originating Socket에는 ACK를 반환하고, 나머지 채팅 Room Socket에는 이벤트를 전송하는 방식을 문서화한다.

이미지 HTTP 요청에서는 채팅 Room 전체에 `chat:message:new`을 전송한다.

### `chat:room:new`

신규 채팅방이 처음 생성되었을 때만 보낸다.

```json
{
  "chatRoom": {
    "chatRoomIdx": 10,
    "listing": {
      "listingIdx": 1,
      "listingType": "USED",
      "title": "상품명",
      "thumbnailUrl": "/resources/example.jpg"
    },
    "opponent": {
      "userIdx": 2,
      "nickname": "감자왕",
      "profileImageUrl": null
    },
    "lastMessage": null,
    "unreadCount": 0,
    "transaction": null,
    "createdAt": "2026-07-30T00:00:00.000Z"
  }
}
```

### `chat:room:updated`

채팅방 생성 이벤트가 아니다.

기존 채팅방의 목록 표시용 요약 정보가 변경되었음을 알린다.

변경 원인:

- 새 메시지
    
- 이미지 메시지
    
- 거래 요청 시스템 메시지
    
- 거래 완료 시스템 메시지
    
- 읽음 처리
    
- 최근 메시지 변경
    

```json
{
  "chatRoomIdx": 10,
  "lastMessage": {
    "messageIdx": 150,
    "messageType": "TEXT",
    "contentPreview": "안녕하세요",
    "senderIdx": 2,
    "createdAt": "2026-07-30T00:00:00.000Z"
  },
  "unreadCount": 3,
  "updatedAt": "2026-07-30T00:00:00.000Z"
}
```

수신자와 발신자의 `unreadCount`가 다르므로 각 사용자 Room에 맞춤 payload를 따로 전송한다.

`chat:read:updated`는 현재 UI에서 상대방의 메시지별 읽음 표시 요구가 없으므로 이번 MVP 이벤트 목록에 추가하지 않는다.

# 10. 경매 정책

## 10.1 경매 시간

- 경매 시작 시각: 서버 시각
    
- 경매 종료 시각: `started_at + 24시간`
    
- 클라이언트 요청 시각은 입찰 허용 판단에 사용하지 않음
    
- 서버가 요청을 처리하는 시각과 `ends_at`을 비교
    

진행 시간은 다음 상수 또는 설정 모듈로 분리하는 방향을 문서화한다.

```text
AUCTION_DURATION_HOURS=24
```

## 10.2 입찰 단위

현재 최고가 기준으로 최소 입찰 단위를 결정한다.

|현재 최고 입찰가|최소 입찰 단위|
|---|--:|
|10,000원 미만|500원|
|10,000원 이상 50,000원 미만|1,000원|
|50,000원 이상 100,000원 미만|2,000원|
|100,000원 이상 500,000원 미만|5,000원|
|500,000원 이상 1,000,000원 미만|10,000원|
|1,000,000원 이상|현재가의 약 1%|

마지막 “약 1%”의 반올림 단위가 아직 정확하지 않다. 이 항목만 `미결정 정책`으로 다시 이동한다.

구현 함수 후보:

```text
calculateBidUnit(currentPrice)
calculateMinimumBid(currentPrice)
```

`auction_posts.bid_unit`은 고정 생성값이 아니라 **현재 가격 기준의 현재 최소 입찰 단위**로 정의하고, 입찰 성공 시 새 현재가에 맞춰 함께 갱신한다.

Redis 경매 상태에는 계산 가능한 `bidUnit`, `minNextBid`를 저장하지 않는다.

## 10.3 Redis Lua

Lua Script 또는 동등한 원자 처리에서 다음을 한 번에 검증·갱신한다.

1. 경매 상태가 `ON_GOING`
    
2. 서버 시각이 `endsAt` 미만
    
3. 입찰자가 판매자가 아님
    
4. 정지·탈퇴 사용자가 아님
    
5. bidPrice가 minNextBid 이상
    
6. 현재가 갱신
    
7. 최고 입찰자 갱신
    
8. bidUnit과 minNextBid 재계산에 필요한 값 반환
    
9. 이전 최고 입찰자 반환
    

Redis의 이전 최고 입찰 기록을 삭제한다는 표현은 사용하지 않는다.

모든 입찰 이력은 `auction_bids`에 계속 보존한다.

## 10.4 DB 저장 실패

DB 저장 실패는 입찰 경쟁에서 패배한 것이 아니라 다음과 같은 실제 장애를 의미한다.

- DB 연결 실패
    
- INSERT 실패
    
- Transaction rollback
    
- 제약조건 충돌
    
- timeout
    

단순 catch에서 Redis를 과거 값으로 무조건 덮어쓰는 보상 로직은 문서화하지 않는다. 후속 입찰을 덮어쓸 위험이 있기 때문이다.

MVP:

- Redis 성공 후 PostgreSQL 즉시 저장
    
- DB 실패 시 오류 로그
    
- 해당 입찰 요청 실패 응답
    
- 안전한 복구는 고도화 항목
    

고도화:

- 실패한 입찰의 requestId가 Redis 현재 상태와 동일한 경우만 조건부 보상
    
- 경매별 sync error 상태
    
- 신규 입찰 임시 차단
    
- PostgreSQL 기준 Redis 재구축
    
- Redis Stream 재시도 Worker
    

## 10.5 Redis Stream과 Worker

기본 구현은 즉시 DB 저장이다.

Redis Stream + Worker는 사용자가 별도로 학습하고 적용할 고도화 구조로 남긴다.

개념 구조:

```text
API Server
-> Redis 원자 입찰 처리
-> Redis Stream XADD
-> Worker XREADGROUP
-> PostgreSQL 저장
-> XACK
```

문서에는 다음을 포함한다.

- Stream은 작업을 저장하는 append-only log
    
- Worker는 별도 프로세스
    
- Consumer Group
    
- Pending Entry
    
- XACK
    
- 재시도
    
- 중복 처리 방지
    
- DB 저장 전 API 성공 응답이 갖는 위험
    

핵심 MVP의 정합성이 Worker 구현에 의존하지 않게 한다.

# 11. 경매 종료 Scheduler

기존 “Node 내부 cron 스케줄러” 표현을 다음 구조로 구체화한다.

## 11.1 1차 실행: 경매별 타이머

경매 생성 성공 후:

```text
AuctionScheduler.schedule(listingIdx, endsAt)
```

서버 메모리에 다음 자원을 관리한다.

```text
Map<listingIdx, Timeout>
```

종료 시각에 해당 경매 종료 Service를 호출한다.

24시간 타이머는 Node `setTimeout`의 지원 범위 안에 있다.

## 11.2 서버 재시작 복구

서버 시작 시:

1. PostgreSQL에서 `ON_GOING` 경매 조회
    
2. 이미 ends_at이 지난 경매는 즉시 종료 시도
    
3. 아직 남은 경매는 타이머 재등록
    

## 11.3 주기적 복구 검사

타이머 누락이나 이벤트 루프 지연을 보완하기 위해 낮은 빈도의 reconciliation scheduler를 둔다.

예:

- 1분마다 `status=ON_GOING AND ends_at <= NOW()` 조회
    
- 정상 타이머의 주 실행 방식이 아니라 복구 안전망
    

## 11.4 멱등성

종료 Service는 여러 번 호출되어도 한 번만 상태 변경해야 한다.

조건부 UPDATE 또는 DB row lock을 사용한다.

예:

```sql
UPDATE auction_posts
SET status = 'FINISHED'
WHERE listing_idx = $1
  AND status = 'ON_GOING'
  AND ends_at <= NOW()
RETURNING *;
```

반환 행이 없으면 이미 종료·취소되었거나 아직 종료 시각이 아니다.

다중 서버 확장 시:

- BullMQ delayed job
    
- PostgreSQL advisory lock
    
- Redis distributed lock
    
- Scheduler 전용 Worker
    

를 고도화 항목으로 남긴다.

# 13. 알림 정책

## 13.1 저장 순서

모든 알림은 PostgreSQL에 먼저 저장한다.

```text
도메인 상태 저장
-> notifications INSERT
-> DB commit
-> Socket 이벤트 전송
```

사용자가 미접속이면 Socket 이벤트는 전달되지 않지만 DB의 `is_read=false`가 유지된다.

## 13.2 NEW_MESSAGE 저장 단위

채팅 메시지 한 건당 `NEW_MESSAGE` notification row 한 건을 생성한다.

메시지를 정확히 마지막 messageIdx까지 읽음 처리하기 위해:

```text
notification_type = NEW_MESSAGE
reference_type = CHAT_MESSAGE
reference_idx = chat_messages.idx
```

로 정의한다.

기존 `CHAT_ROOM` 참조는 `NEW_CHAT_ROOM` 등에 사용한다.

알림 목록 조회 시 `NEW_MESSAGE`는 `chat_messages`와 `chat_rooms`를 JOIN해 같은 채팅방별로 집계한다.

집계 항목:

- chatRoomIdx
    
- 상대방
    
- 마지막 메시지 preview
    
- unread message count
    
- 마지막 알림 시각
    
- 대표 notificationIdx 또는 group key
    

## 13.3 같은 채팅방을 보고 있을 때

사용자가 같은 채팅방 Room에 있다고 해서 DB 저장 전에 알림을 생략하지 않는다.

흐름:

1. 메시지 저장
    
2. NEW_MESSAGE 알림 저장
    
3. Socket 전송
    
4. React가 메시지 렌더링
    
5. `chat:read`
    
6. 해당 messageIdx까지 notification 읽음 처리
    

접속 상태 판단이 틀려도 영속 데이터 정합성이 깨지지 않게 한다.

## 13.4 알림 Socket 이벤트

### `notification:new`

대상:

```text
user:{receiverIdx}
```

일반 알림 예:

```json
{
  "notificationIdx": 1,
  "notificationType": "OUTBID",
  "referenceType": "LISTING",
  "referenceIdx": 10,
  "content": "최고 입찰자가 변경되었습니다.",
  "isRead": false,
  "createdAt": "2026-07-30T00:00:00.000Z"
}
```

채팅 메시지 알림은 UI 집계를 돕기 위해 다음 보조 필드를 포함할 수 있다.

```json
{
  "notificationIdx": 2,
  "notificationType": "NEW_MESSAGE",
  "referenceType": "CHAT_MESSAGE",
  "referenceIdx": 150,
  "chatRoomIdx": 10,
  "senderIdx": 2,
  "contentPreview": "안녕하세요",
  "stackCount": 3,
  "isRead": false,
  "createdAt": "2026-07-30T00:00:00.000Z"
}
```

### `notification:unread-count`

절대값을 보낸다.

```json
{
  "unreadCount": 7
}
```

다음 상황마다 재계산 후 전송한다.

- 새 알림 생성
    
- 단건 읽음
    
- 전체 읽음
    
- 채팅방 읽음
    

증가량 `+1`, `-3` 방식은 사용하지 않는다.

### 제거

```text
notification:read
```

알림 읽음 처리는 HTTP 또는 채팅의 `chat:read`로 통일한다.

삭제:

```text

```

기존 인덱스와 중복 여부를 확인해 적절히 통합한다.

## 15.4 auction_posts.bid_unit

성공 입찰 시 다음을 함께 갱신한다.

## 15.5 transactions

기존 부분 UNIQUE 인덱스를 유지한다.

```sql
CREATE UNIQUE INDEX uq_transactions_active_listing
```

하나의 상품에 활성 거래가 두 개 이상 생기지 않게 한다.

## 15.6 ERD 오류 수정

다음 잘못된 자기참조 관계를 제거한다.

```text
Ref: "transactions"."idx" < "transactions"."seller_idx"
```

ERD의 DBML, 하단 설명 목록, 이미지 기준 설명이 서로 일치하는지 확인한다.

# 23. Socket.IO 다중 서버 확장 문서

MVP는 단일 Socket.IO 서버다.

다중 서버 확장 시:

```text
Load Balancer
-> Socket.IO Server 1
-> Socket.IO Server 2
-> Socket.IO Server 3
<-> Redis Adapter Pub/Sub
```

설명:

- 각 서버는 자기 서버 Socket과 Room만 메모리에 보관
    
- Redis에 모든 socketId를 직접 저장하지 않음
    
- `@socket.io/redis-adapter`는 직접 실행한 Redis 서버에 연결
    
- Redis Pub/Sub로 서버 간 이벤트 전달
    
- 라이브러리가 Redis 서버를 직접 실행하지 않음
    
- HTTP long-polling을 허용하면 sticky session 필요
    
- WebSocket 연결은 하나의 지속 연결
    
- Socket.IO는 기본적으로 polling 후 WebSocket upgrade 가능
    
- Redis Adapter는 연결 세션 자체를 공유하는 기능이 아님
    

이 내용은 “현재 구현”과 “트래픽 증가 대비 구조”를 구분해 작성한다.

동시 접속 1만 명을 검증하지 않은 상태에서 “1만 명을 처리한다”고 단정하지 않는다.

발표 표현 예:

```text
현재 MVP는 단일 서버로 구현하지만, 트래픽 증가 시 Load Balancer와
Socket.IO Redis Adapter를 사용해 Socket 서버를 수평 확장할 수 있도록
Room과 이벤트 전달 구조를 분리했습니다. 실제 수용량은 부하 테스트를
통해 검증합니다.
```

# 27. 최종 정합성 검사

수정 후 저장소 전체에서 다음 문자열을 검색한다.

폐기 대상:

```text
check-nickname
check-email
find-password
PATCH /api/auth/password
PATCH /api/auctions/:listingIdx
판매자 경매 취소
POST /api/chats/:chatRoomIdx/messages
/api/uploads/images
connect:success
presence:ping
notification:read
disabledActions
chat_messages.deleted_at
banned_until
transactions"."idx" < "transactions"."seller_idx
```

주의:

`PATCH /api/auctions/:listingIdx` 검색 시 관리자 취소 경로는 제거하지 않는다.

다음 항목의 명칭과 방향이 모든 문서에서 동일한지 검사한다.

```text
chat:read              Client -> Server
chat:room:new          Server -> Client
chat:room:updated      Server -> Client
chat:message:new       Server -> Client
auction:join           Client -> Server
auction:bid-updated    Server -> Client
notification:new       Server -> Client
notification:unread-count Server -> Client
```

다음 상태 철자를 통일한다.

```text
ON_SALE
SOLD
CANCELED
ON_GOING
FINISHED
REQUESTED
COMPLETED
```

오타 후보를 제거한다.

```text
userd_posts
CALCELED
is_activate
pasſtword 또는 passtword
일지 않음
```

Obsidian 링크가 깨지지 않았는지 확인한다.
