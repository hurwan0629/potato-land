# 최종 원칙과 용어

## 1. 최종 통합 원칙

1. `integration/hurwan/team-merge`를 기준선으로 삼는다.
2. 기능 브랜치를 통째로 merge하지 않는다. 실행 가능한 로직과 UI만 선별 반영한다.
3. 공통 인프라가 존재하면 도메인 폴더에서 DB·Redis·upload·logger를 다시 만들지 않는다.
4. 외부 CSS는 유지한다. 프런트 변경은 JSX, API client, routing, 데이터 매핑을 우선한다.
5. 문서와 코드가 다르면 우연히 구현을 따라가지 않는다. 최종 계약을 결정하고 양쪽을 함께 수정한다.
6. DB transaction 안에는 DB 일관성에 필요한 작업만 둔다. Socket·Redis cache·파일 정리처럼 되돌리기 어려운 작업은 commit 이후 수행한다.
7. 외부 부수효과 실패는 로그와 복구 경로를 남긴다. 이미 commit된 DB 결과를 거짓으로 실패 처리하지 않는다.

## 2. 식별자 용어

| 이름 | 의미 | 사용 위치 |
|---|---|---|
| `userIdx` | 사용자 PK | URL, DTO, `req.user.userIdx` |
| `listingIdx` | 중고·경매 공통 상품 PK | URL, favorites, chat room, transaction |
| `transactionIdx` | 거래 PK | 결제·후기·시스템 메시지 |
| `chatRoomIdx` | 채팅방 PK | HTTP와 Socket room |
| `phoneVerificationId` | 특정 전화번호와 purpose의 SMS 인증 완료 증명 | 회원가입·전화번호 변경·아이디 찾기·비밀번호 재설정 |
| `editToken` | 현재 비밀번호 확인 후 발급하는 10분 회원정보 수정 권한 | 회원정보 수정·탈퇴 |
| `sessionId` | Refresh session 식별자 | JWT `sid`, Redis session key |

## 3. `phoneVerificationId`와 `editToken`

둘은 대체 관계가 아니다.

- `phoneVerificationId`는 **전화번호 소유 확인**이다.
- `editToken`은 **현재 계정 비밀번호 확인**이다.
- 전화번호를 변경할 때는 둘 다 필요하다.

최종 회원정보 수정 요청 예시:

```json
{
  "editToken": "member-edit-jwt",
  "nickname": "감자",
  "phone": "01012345678",
  "phoneVerificationId": "phone-proof-id",
  "email": "potato@example.com",
  "newPassword": "new-password",
  "newPasswordConfirm": "new-password"
}
```

`phone`이 기존 값과 같으면 `phoneVerificationId`는 생략할 수 있다. 비밀번호를 바꾸지 않으면 `newPassword`, `newPasswordConfirm`을 생략할 수 있다.
