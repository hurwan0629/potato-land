# 인증과 토큰 계약

## 1. 보호 API 인증

1. `access_token` HttpOnly cookie를 읽는다.
2. JWT 서명, 만료, `type=access`, `sub`, `sid`를 확인한다.
3. DB에서 현재 사용자를 조회한다.
4. 탈퇴 사용자는 401, 정지 사용자는 403으로 차단한다.
5. `req.auth`와 `req.user`를 만든다.
6. Controller로 진행한다.

```js
req.auth = {
  sub: "12",
  sid: "session-id",
  type: "access"
};

req.user = {
  userIdx: 12,
  nickname: "감자",
  profileImageUrl: "/resources/profiles/12.webp",
  role: "USER"
};
```

## 2. 선택 인증

공개 목록·상세 API는 access token이 없으면 비로그인으로 진행한다. token이 있다면 필수 인증과 동일하게 DB 사용자 상태까지 확인한다. 잘못되거나 만료된 token은 비로그인으로 조용히 무시하지 않고 401을 반환한다. 오래된 인증 cookie를 숨긴 채 viewer 권한을 계산하면 클라이언트 상태가 불일치하기 때문이다.

## 3. 역할 검사

`requireRole("ADMIN")`은 반드시 `requireAuth` 뒤에 배치한다. JWT에 들어 있던 오래된 role이 아니라 DB에서 정규화한 `req.user.role`을 검사한다.

## 4. 회원정보 수정

1. 사용자가 현재 비밀번호를 보낸다.
2. 서버가 bcrypt로 확인한다.
3. 서버가 10분 `editToken`을 발급한다.
4. 사용자가 수정 요청에 `editToken`을 보낸다.
5. 전화번호가 바뀌면 `CHANGE_PHONE` purpose의 `phoneVerificationId`도 확인하고 소비한다.
6. 비밀번호가 바뀌면 모든 Refresh session을 폐기하고 재로그인을 요구한다.

최종 파라미터는 `newPassword`, `newPasswordConfirm`이다. 기존 구현의 `password`, `passwordConfirm`은 호환 입력으로 한시 지원할 수 있지만 응답 문서와 프런트는 최종 이름을 사용한다.
