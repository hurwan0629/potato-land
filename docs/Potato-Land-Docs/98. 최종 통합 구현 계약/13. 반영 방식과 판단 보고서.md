## `feat/front-mypage-admin`

- 확인된 주요 작성 계정: `Jeabin90`
- 반영: 관리자·마이페이지·후기 SQL 의도, 관리자/마이페이지 UI 방향, API client 방향
- 재작성: Controller 대형 SQL을 Controller → Service → Repository로 분리
- 수정: `req.user.idx` → `req.user.userIdx`, Router 전체 관리자 guard, session/Timer/Redis 후처리
- 판단: 실제 스키마와 사용 흐름을 고민한 흔적이 있어 가장 많이 보존했다. 다만 계층과 인증 계약은 현재 정본과 달라 형태 그대로 복사하지 않았다.

## `feat/main-used`

- 확인된 주요 작성 계정: `eiruuubp`
- 반영: Home/Search/상세/등록 화면의 사용자 의도와 상품 카드 표현
- 미반영: mock 배열 backend, 하드코딩 URL, 임의 `x-user-idx`, 커밋된 conflict marker
- 최종 구현: PostgreSQL repository와 공통 인증/upload로 9개 API를 새로 구현
- 판단: 프런트 기여는 보존 가치가 높지만 backend는 실행·일관성 기준을 충족하지 못해 새로 구현하는 편이 안전했다.

## `feat/auction`

- 확인된 주요 작성 계정: `YsuY`
- 반영: 경매 등록·조회·수정·삭제·입찰에서 확인해야 할 정책 의도
- 미반영: `query(SELECT)`, `query(UPDATE)`, 선언되지 않은 auth/db/io/storage, 중첩 client 프로젝트
- 최종 구현: 기준 브랜치의 경매 repository/service를 확장해 row lock 입찰, 낙찰 거래, recovery를 구현
- 판단: 백엔드까지 고려한 흔적은 문서와 주석에 보존했지만 실행 불가능 placeholder를 최종 코드에 남기는 것은 기여 보존이 아니라고 판단했다.

## 이미 통합돼 있던 코드

인증·채팅·거래·알림은 기준 브랜치 구현을 유지했다. 다만 다음 공통 결함은 수정했다.

- JWT-only 미들웨어와 DB 검증 미들웨어 이중화 제거
- SMS 인증번호 로그 노출 제거
- `/resources`와 upload root 통일
- 도메인별 Multer 중복 제거
- recovery scheduler 실제 시작

## CSS 판단

기존 `.css` 파일은 수정하지 않았다. JSX와 API 연결만 변경해 팀원이 만든 외부 표현을 최대한 보존했다.
