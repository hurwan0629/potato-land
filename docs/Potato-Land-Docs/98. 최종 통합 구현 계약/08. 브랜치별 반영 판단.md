# 브랜치별 반영 판단

## 기준선

- `integration/hurwan/team-merge@7b06672`

## `feat/front-mypage-admin`

### 반영

- 마이페이지 조회 SQL의 의도
- 관리자 대시보드·회원·상품 관리 쿼리
- 후기 작성 transaction
- 마이페이지·관리자 UI와 API client

### 수정 후 반영

- `req.user.idx`를 최종 계약 `req.user.userIdx`로 변경
- Router에 `requireAuth`, `requireRole("ADMIN")` 적용
- Controller SQL을 Service·Repository로 분리
- 정지·삭제 이후 session, Redis, Timer, Socket 후처리 추가

### 판단

실제 DB 스키마를 고려한 코드가 있어 가장 높은 비율로 활용한다. 다만 오래된 인증 객체와 계층 혼합은 그대로 유지하지 않는다.

## `feat/main-used`

### 반영

- Home, Search, 상품 상세, 상품 등록 UI 구성
- ProductCard 표현 방식

### 미반영

- mock 배열 기반 backend
- 해결되지 않은 merge conflict marker
- 하드코딩된 `localhost:8081`
- `x-user-idx` 임의 인증

### 판단

외부 화면 기여는 보존하되 backend는 현재 DB·인증 계약으로 다시 구현하는 편이 더 안전하다.

## `feat/auction`

### 반영

- 경매 화면·입력 필드 의도
- 판매자·종료 상태·입찰 검증을 고려한 흔적

### 미반영

- `db.query(SELECT)`, `connection.query(UPDATE)` 형태의 실행 불가능 placeholder
- 선언되지 않은 auth/db/io/storage 의존성
- 중첩된 `client/po1-main/client` 프로젝트

### 판단

기여 의도와 UI는 기록하되 실행 코드는 기준선 경매 모듈을 확장해 다시 구현한다.

## 기여 보존 방식

원본 브랜치는 그대로 남긴다. 최종 변경 보고서에는 반영 파일, 재작성 부분, 판단 이유를 기록한다. 잘못된 코드 형태를 보존하는 대신 유효한 정책·쿼리·UI 기여를 최종 구조에 맞게 보존한다.
