# E-04 알림 저장·전송·읽음

## 원칙

알림의 원본은 DB다. Socket은 접속 중 사용자에게 새 알림과 절대 unread count를 빠르게 전달할 뿐이다.

## Frontend 흐름

- 최초 진입과 재연결 시 HTTP로 알림 목록과 unread count를 조회한다.
- `notification:new`은 notificationIdx 중복을 무시하고, unread count 이벤트는 증감이 아닌 최종값으로 덮어쓴다.
- 알림 클릭/전체 읽음은 HTTP API를 호출하고 성공 응답으로 목록을 보정한다.

## Backend 흐름

도메인 서비스는 아래 저장 순서를 사용하고, 읽음 API는 인증 사용자의 알림만 변경한다.

## 알림 생성 순서

1. 도메인 서비스가 고정된 `notificationType`, `referenceType`, `referenceIdx`, 수신자를 결정한다.
2. 핵심 상태 변경과 같은 DB transaction에 `notifications(is_read=false)`를 저장한다.
3. commit 후 생성 DTO를 `user:{userIdx}`에 `notification:new`으로 보낸다.
4. DB의 미확인 알림 수를 조회해 `notification:unread-count` 절대값을 보낸다.

도메인 서비스가 직접 임의 문자열 type을 만들지 않도록 공통 `notificationEmitter`를 사용한다.

## 고정 타입

- 송금 요청: `PAYMENT_REQUESTED`
- 거래 완료 판매자 수신: `PAYMENT_RECEIVED`
- 송금 요청 취소 구매자 수신: `PAYMENT_CANCELED`
- 후기: `NEW_REVIEW`
- 입찰: `NEW_BID`, `OUTBID`
- 경매: `AUCTION_WON`, `AUCTION_ENDED`, `AUCTION_ENDED_WITHOUT_BID`, `AUCTION_LEADER_CHANGED`
- 삭제: `LISTING_DELETED`

위 목록에 없는 유사 별칭을 추가하지 않는다.

## NEW_MESSAGE 예외

1. 메시지는 언제나 DB에 저장한다.
2. 수신자의 연결 중 하나라도 해당 `activeChatRoomIdx`를 보고 있으면 `NEW_MESSAGE` 알림 row만 생략한다.
3. 보고 있지 않으면 메시지 transaction 안에 알림을 저장한다.
4. 이 판단이 순간적으로 어긋나도 메시지와 `chat_room_reads`가 최종 unread 계산 기준이다.

## 읽음 API 처리

1. 인증 사용자가 본인 알림만 선택할 수 있게 조건을 건다.
2. 단건/전체 읽음 update를 transaction으로 수행한다.
3. commit 후 DB에서 unread count를 다시 계산한다.
4. 사용자의 모든 연결에 최종값을 보낸다.
5. 이미 읽은 알림 요청은 성공으로 처리해 재요청을 안전하게 만든다.

## 실패 원칙

- 핵심 transaction rollback이면 알림도 저장·전송하지 않는다.
- commit 후 Socket 실패는 알림 DB 상태에 영향을 주지 않는다.
- unread count 계산 실패 시 임의 증감값을 보내지 않고 다음 HTTP 조회/이벤트에서 회복한다.
- Redis에 알림 목록이나 unread count를 중복 저장하지 않는다.
