# E-01 채팅방 조회·입장·퇴장

## 요청 계약

- 방 정보: `GET /api/chats/:chatRoomIdx`
- 메시지: `GET /api/chats/:chatRoomIdx/messages?page=&limit=`
- Socket: `chat:join`, `chat:leave`

## Frontend 순서

1. HTTP로 방 정보와 메시지를 조회한다.
2. `readOnly`, `canSendMessage`, `canCreatePaymentRequest`로 입력창과 버튼을 구성한다.
3. Socket 연결 후 `chat:join { chatRoomIdx }`를 보낸다.
4. join ack가 성공하면 마지막 메시지 기준 `chat:read`를 보낸다.
5. 화면 이탈 시 `chat:leave`를 보내고 이벤트 리스너를 해제한다.
6. Socket 재연결 시 HTTP 메시지 목록을 다시 조회한 후 join한다.

## HTTP Backend 순서

1. 인증·활성 사용자와 room id를 검증한다.
2. `chat_rooms`에서 seller/buyer 참여자인지 확인한다.
3. listing, 양 참여자, 연결 transaction을 조회한다.
4. 삭제 상품이나 비활성 상대방이어도 과거 방과 메시지 조회는 허용한다.
5. 다음 우선순위로 쓰기 권한을 계산한다.

| 조건 | 결과 |
|---|---|
| 참여자 비활성 | read-only |
| listing 삭제 | read-only |
| 중고글 거래 가능 | 일반 채팅 가능 |
| 진행 경매 | 일반 채팅 가능 |
| 종료 경매 + 판매자/낙찰자 정산 거래 `REQUESTED` | 정산 채팅 가능 |
| 종료 경매의 그 외 방 | read-only |
| 거래 완료/취소 후 추가 대화 정책 미지정 | 안전하게 read-only, 변경 시 정책 문서 동시 수정 |

6. 판매자이면서 활성 송금 요청이 없고 상품 정책이 허용할 때만 `canCreatePaymentRequest=true`로 응답한다.

## Socket join/leave 순서

1. `socket.data.user` 활성 상태를 확인한다.
2. DB에서 채팅방 참여자 여부를 다시 확인한다.
3. `socket.join("chat:{chatRoomIdx}")` 후 `activeChatRoomIdx`를 설정한다.
4. 현재 read-only 상태와 `lastReadMessageIdx`를 ack한다.
5. leave 시 room에서 나가고 active id가 같을 때만 null로 정리한다.
6. disconnect 시 메모리 상태는 소멸한다. Redis presence는 만들지 않는다.
