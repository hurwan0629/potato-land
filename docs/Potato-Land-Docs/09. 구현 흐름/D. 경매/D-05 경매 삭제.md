# D-05 경매 삭제

## 목적

판매자 또는 관리자가 경매를 soft delete하고 신규 조회·입찰·일반 채팅을 차단하되 기존 이력은 보존한다.

## 요청 계약

`DELETE /api/auctions/:listingIdx`

```json
{
  "deleteReason": "판매자가 직접 삭제"
}
```

## Frontend 구현 흐름

1. 삭제 권한이 있을 때만 확인 모달을 표시한다.
2. 요청 중 중복 클릭을 막는다.
3. 성공하면 목록 캐시에서 제거하고 상세 이동을 차단한다.
4. 다른 화면에서 `auction:deleted`를 받으면 입찰·일반 채팅·관심·정산 생성 버튼을 모두 잠근다.
5. 기존 거래/채팅 내역의 과거 기록은 유지하되 상품 상세 링크는 비활성화한다.

## Backend 실행 순서

1. 인증·활성 사용자와 `listingIdx`를 검증한다.
2. DB에서 경매와 판매자를 조회한다.
3. 이미 삭제된 경매는 일반 조회와 동일하게 `404`로 처리한다.
4. 판매자 본인 또는 관리자인지 확인한다.
5. transaction을 시작한다.
6. `listings.deleted_at`, `deleted_by`, `delete_reason`을 저장한다.
7. 관련 `favorites`를 삭제한다.
8. 진행 중이었다면 `auction_bids`에서 distinct 입찰자를 조회해 사용자당 `LISTING_DELETED` 알림 한 건을 저장한다.
9. 기존 `auction_bids`, `transactions`, `chat_rooms`, `chat_messages`, `reviews`는 삭제하지 않는다.
10. commit한다.
11. 진행 Timer를 제거하고 Redis 경매 state를 삭제한다.
12. 경매 room에 `auction:deleted`, 알림 대상 개인 room에 알림과 절대 unread count를 전송한다.

## 동시 요청 분기

- 입찰과 삭제가 겹치면 DB의 경매 row 잠금 또는 조건부 update로 둘 중 하나만 먼저 확정한다.
- 삭제가 먼저 확정되면 입찰 transaction 재검증이 실패해야 한다.
- 입찰이 먼저 확정되면 삭제는 그 입찰 이력을 포함해 대상 알림을 계산한다.
- 삭제 성공 이후 Redis에 잠시 state가 남아도 입찰 API의 DB 삭제 검증이 먼저 차단한다.

## 실패 분기

| 조건 | 결과 |
|---|---|
| 권한 없음 | `403 FORBIDDEN` |
| 없음/이미 삭제 | `404 NOT_FOUND` |
| DB rollback | Redis·Timer·Socket 변경 없음 |
| commit 후 Redis/Timer 정리 실패 | 삭제 DB 상태 유지, 정리 재시도 로그 |
