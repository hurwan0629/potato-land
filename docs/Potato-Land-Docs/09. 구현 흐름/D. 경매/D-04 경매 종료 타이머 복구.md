# D-04 경매 종료·Timer 복구

## 목적

DB의 `ends_at`을 기준으로 경매를 한 번만 종료하고 낙찰 결과를 확정한다. 종료 시 거래나 채팅방을 자동 생성하지 않는다.

## Frontend 구현 흐름

1. 카운트다운은 상세 응답의 `endsAt`으로 표시한다.
2. 0초가 되어도 프론트가 낙찰자를 결정하거나 상태를 저장하지 않는다.
3. 버튼을 잠근 뒤 `auction:ended` 또는 상세 재조회 결과를 기다린다.
4. 판매자는 낙찰자가 있을 때 `canCreateSettlement` 버튼으로 별도 송금 요청을 생성한다.
5. 낙찰자는 판매자가 요청을 만들기 전까지 낙찰 안내만 확인한다.

## 단일 종료 서비스

Timer와 Recovery Scheduler는 모두 `finishAuction(listingIdx, now)` 하나만 호출한다.

1. DB transaction을 시작하고 대상 `auction_posts` row를 잠근다.
2. 삭제 글, 이미 `FINISHED`, 아직 `ends_at` 이전이면 아무 변경 없이 종료한다.
3. DB의 유효 입찰 이력을 기준으로 최종 최고 입찰을 확인한다. Redis 값은 빠른 후보일 뿐 최종 판정은 DB로 검증한다.
4. `auction_posts.status = FINISHED`, 최종 `current_price`, `winning_bid_idx`를 저장한다.
5. 낙찰자가 있으면 판매자와 낙찰자에게 `AUCTION_ENDED`/`AUCTION_WON` 알림을 DB에 저장한다.
6. 입찰이 없으면 판매자에게 `AUCTION_ENDED_WITHOUT_BID` 알림을 저장한다.
7. commit한다.
8. Redis `auction:state:{listingIdx}`를 삭제하고 Timer map에서 제거한다.
9. 경매 room에 `auction:ended`, 낙찰자 개인 room에 `auction:won`, 관련 `notification:new`을 전송한다.

`transactions`, `chat_rooms`, `chat_messages`는 종료 서비스에서 만들지 않는다. 판매자의 후속 요청이 별도 거래 생성 경계다.

## Timer 등록과 복구

- 등록 commit 후 `ends_at - now`로 Timer를 등록한다.
- `auctionTimers`에는 `listingIdx`, `timeoutId`만 둔다.
- 서버 시작 시 DB에서 `ON_GOING`이고 삭제되지 않은 경매를 조회한다.
- `ends_at`이 미래면 Timer를 다시 등록한다.
- 이미 지났으면 `finishAuction`을 즉시 호출한다.
- 주기 Recovery Scheduler도 종료 누락 row만 찾아 같은 서비스를 호출한다.
- row lock과 상태 조건 때문에 Timer와 Scheduler가 동시에 실행돼도 한 번만 상태가 바뀐다.

## 실패 분기

| 실패 지점 | 처리 |
|---|---|
| DB transaction 실패 | 종료 이벤트·Redis 삭제 금지, 다음 Recovery에서 재시도 |
| commit 후 Redis 삭제 실패 | DB는 이미 최종 기준, 삭제 재시도 로그 남김. 입찰 API는 DB `FINISHED`로 차단 |
| commit 후 Socket 실패 | DB 알림 유지, 재접속/HTTP 조회로 회복 |
| Timer 프로세스 유실 | Recovery Scheduler 또는 서버 시작 복구 |

- [ ] 종료 시 거래 자동 생성 금지
- [ ] 판매자가 별도 정산 요청 생성
