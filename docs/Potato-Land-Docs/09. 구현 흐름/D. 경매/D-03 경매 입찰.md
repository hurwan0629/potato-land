# D-03 경매 입찰

## 목적

동시 입찰의 승자를 Redis에서 원자적으로 결정하고, 성공한 입찰만 DB에 영속화한 뒤 Socket으로 전파한다.

## 요청 계약

`POST /api/auctions/:listingIdx/bids`

```json
{
  "bidAmount": 21000
}
```

- 쿠키 인증과 `credentials: "include"`가 필수다.
- `bidAmount`는 원 단위 양의 정수다.
- 프론트가 보내는 현재가나 최고 입찰자 값은 신뢰하지 않는다.

## Frontend 실행 순서

1. `canBid`가 true일 때만 form을 연다.
2. 화면의 `minNextBid`로 1차 검증하되 서버 재검증이 최종임을 전제로 한다.
3. 요청 중 버튼을 잠근다.
4. 성공 응답의 `bidIdx`가 현재 화면의 마지막 `bidIdx`보다 클 때 가격을 반영한다.
5. 동일 입찰의 `auction:bid-updated`가 뒤늦게 와도 `bidIdx`로 중복을 무시한다.
6. `BID_TOO_LOW`이면 응답 details의 최신 가격을 표시한다.
7. `AUCTION_CLOSED`이면 버튼과 입력을 닫고 상세를 재조회한다.
8. `REDIS_UNAVAILABLE`이면 가격을 임의 갱신하지 않고 재시도 안내만 한다.

## Backend 사전 검증

1. Access Token과 DB의 활성 사용자 상태를 확인한다.
2. `listingIdx`, `bidAmount` 형식과 범위를 검증한다.
3. DB에서 `listings`, `auction_posts`, 판매자를 조회한다.
4. 삭제된 경매는 `404`, 판매자 본인은 `403`을 반환한다.
5. DB `status === ON_GOING`이고 서버 현재 시각이 `ends_at` 이전인지 확인한다.
6. Redis 연결을 확인한다. 사용할 수 없으면 DB만으로 입찰을 받지 않고 `503`을 반환한다.

## Redis 원자 처리

Key는 `auction:state:{listingIdx}`이며 Hash 필드는 다음뿐이다.

```text
currentPrice
highestBidderIdx
highestBidIdx
```

1. key가 없으면 DB의 현재가와 winning bid를 기준으로 초기화한다.
2. Lua script에서 현재가를 읽고 서버의 입찰 증가 규칙으로 최소 입찰가를 계산한다.
3. `bidAmount`가 부족하면 Redis를 변경하지 않고 현재가와 최소 입찰가를 반환한다.
4. 충분하면 이전 최고 입찰자 값을 반환하면서 현재가와 최고 입찰자 후보를 원자적으로 갱신한다.
5. 실제 `highestBidIdx`는 DB insert 후 생성되므로 commit 뒤 새 bid id로 보정한다.

## DB와 부수효과 실행 순서

1. Redis 성공 결과를 받은 뒤 DB transaction을 시작한다.
2. transaction 안에서 경매가 아직 `ON_GOING`이고 종료 전인지 다시 확인한다.
3. `auction_bids`를 insert하고 `bidIdx`를 받는다.
4. `auction_posts.current_price`, `winning_bid_idx`를 갱신한다.
5. 이전 최고 입찰자가 다른 사용자이면 `OUTBID` 알림을 저장한다.
6. commit한다.
7. Redis `highestBidIdx`를 생성된 `bidIdx`로 보정한다.
8. `auction:{listingIdx}`에 `auction:bid-updated`를 전송한다.
9. 이전 최고 입찰자의 `user:{userIdx}`에 `auction:outbid`, `notification:new`, 절대 unread count를 전송한다.
10. HTTP 성공 응답을 보낸다.

DB commit 전에 성공 ack나 Socket 이벤트를 보내지 않는다.

## 실패와 범위

| 실패 | 처리 |
|---|---|
| 낮은 입찰가 | `409 BID_TOO_LOW`, 최신 `currentPrice`, `minNextBid` 반환 |
| 종료/삭제/판매자 입찰 | Redis 변경 전 거부 |
| Redis 장애 | `503 REDIS_UNAVAILABLE`, DB 변경 없음 |
| Redis 성공 후 DB 상태 재검증 실패 | 성공 emit 금지, DB rollback, Redis를 DB 값으로 best-effort 재생성 |
| Redis 성공 후 DB 장애 | 위와 동일. 완전한 재처리 보장은 MVP 제외, reconciliation 확장 지점 기록 |
| Socket emit 실패 | DB/Redis 성공은 유지, 클라이언트 재조회로 회복 |

## 저장소 책임

- DB 최종 원본: `auction_bids`, `auction_posts`, `notifications`
- Redis: 진행 중 최고 입찰 projection과 원자 비교
- Socket: commit된 결과 전달만 담당
- Timer: 입찰 요청에서 변경하지 않는다.
