# B-01 목록·검색·상세 조회

## 요청 계약

- 중고 목록/상세: `GET /api/used`, `GET /api/used/:listingIdx`
- 경매 목록/상세: `GET /api/auctions`, `GET /api/auctions/:listingIdx`
- query는 API 명세의 `q`, category, 상태, sort, page, limit만 허용한다. MVP 목록에는 가격 범위 필터가 없다.

## Frontend 순서

1. 필터를 query로 직렬화하고 요청마다 이전 요청을 취소하거나 최신 request만 반영한다.
2. 서버가 준 pagination과 items를 그대로 사용한다.
3. 404 상세는 삭제/미존재를 구분해 노출하지 않고 목록으로 안내한다.
4. 권한 버튼은 상세 응답의 `viewer.canEdit`, `viewer.canDelete`, `viewer.canBid`, `viewer.canChat`, `viewer.canFavorite`를 사용한다.
5. 평점 원본은 `/ 2`해 표시한다.
6. 경매 실시간 처리는 상세 HTTP 성공 뒤 D-02에 따라 연결한다.

## Backend 목록 순서

1. query 형식·허용 sort·page limit을 검증한다.
2. optional token이 있으면 유효성을 확인한다.
3. 모든 일반 목록에 `listings.deleted_at IS NULL`을 강제한다.
4. 타입별 테이블, 대표 이미지, 판매자 표시 DTO를 필요한 범위로 join한다.
5. 비활성 판매자는 `삭제된 사용자`, 프로필 링크 비활성으로 변환한다.
6. 목록은 N+1 없이 집계/서브쿼리로 favoriteCount, bidCount 등을 계산한다.
7. 진행 경매의 매우 최신 현재가가 필요한 상세가 아닌 목록에서는 DB projection을 기본으로 사용해 Redis 다건 조회를 피한다.

## Backend 상세 순서

1. listing id를 검증하고 타입별 row를 조회한다.
2. 삭제 글이면 `404`를 반환한다.
3. optional 사용자 기준 관심 여부와 권한을 계산한다.
4. 중고글은 DB 상태만 사용한다.
5. 진행 경매는 DB 상태/종료 시각을 확인한 후 Redis 세 입찰 필드가 있으면 현재가에 반영한다.
6. Redis miss면 DB 값으로 응답하며, Redis 장애면 입찰을 잠그되 조회 가능한 정보는 반환한다.
7. 경매 `minNextBid`는 선택된 현재가로 서버에서 계산한다.
8. 상품 상태와 희망 거래 위치는 공통 `listings`에서 읽어 중고·경매에 동일한 이름으로 응답한다.

## 동기화 기준

- 목록은 DB의 일관된 snapshot, 경매 상세는 DB + 선택적 Redis projection이다.
- Socket은 목록/상세 초기 데이터를 대체하지 않는다.
- 프론트 refocus·reconnect 시 현재 상세를 HTTP로 다시 확인한다.
