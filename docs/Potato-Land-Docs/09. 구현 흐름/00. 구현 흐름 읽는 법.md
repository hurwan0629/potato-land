# 구현 흐름 읽는 법

> 이 폴더는 화면 설명이 아니라 구현 계약이다. 각 문서는 프론트 요청, 서버 검증 순서, DB/Redis 책임, Socket 전파, 실패 분기를 실제 실행 순서대로 설명한다.

## 1. 공통 처리 순서

기본 변경 요청은 다음 순서를 따른다.

```text
Frontend 입력 검증
-> HTTP/Socket 요청
-> 인증 및 활성 사용자 확인
-> params/query/body 형식 검증
-> DB에서 권한과 영속 상태 확인
-> 필요한 경우 Redis에서 실시간 상태 확인
-> DB transaction으로 핵심 상태와 부수효과 저장
-> commit 후 Redis 정리 또는 갱신
-> commit이 확인된 결과만 Socket으로 전파
-> HTTP 응답
-> Frontend 로컬 상태 반영
```

입찰은 Redis 원자 처리가 선행되므로 예외적으로 다음 순서를 사용한다.

```text
DB에서 경매/사용자/종료 조건 확인
-> Redis Lua로 입찰가 비교 및 최고 입찰 상태 원자 갱신
-> DB transaction으로 입찰 이력과 경매 현재가 저장
-> commit 후 Socket/알림 전파
```

Redis 갱신 뒤 DB 저장이 실패하는 희귀 장애의 완전한 보상·재처리는 MVP 범위에서 제외한다. 이때 Socket 성공 이벤트는 보내지 않고, 가능한 범위에서 DB 값으로 Redis를 다시 만들며, 추후 outbox/재처리 worker를 연결할 수 있도록 서비스 경계를 분리한다.

## 2. 신뢰 기준

| 데이터 | 최종 기준 | Redis/Socket 역할 |
|---|---|---|
| 사용자, 게시글, 거래, 후기 | PostgreSQL | 사용하지 않음 |
| 경매 상태, 시작가, 종료 시각, 입찰 이력 | PostgreSQL | Redis는 진행 중 최고 입찰 projection |
| Refresh session, 전화번호 인증 | Redis | TTL이 있는 임시 인증 상태 |
| 채팅 메시지, 읽음 위치, 알림 | PostgreSQL | Socket은 commit된 결과 전달 |
| 현재 보고 있는 채팅방/경매방 | `socket.data` | 알림 생략과 room 관리에만 사용 |

- Socket payload는 저장소가 아니며 새로고침·재연결 후에는 HTTP API로 복구한다.
- 프론트는 Socket 이벤트를 받더라도 더 최신 HTTP 응답을 과거 이벤트로 덮어쓰지 않는다.
- 입찰 이벤트는 `bidIdx`, 메시지 이벤트는 `messageIdx`를 기준으로 중복·역순 수신을 무시한다.
- 종료·삭제·최고 입찰자 재계산 이벤트를 받은 화면은 버튼을 즉시 잠그고 필요하면 상세 API를 다시 호출한다.

## 3. 인증과 요청 경계

- 보호 HTTP API는 HttpOnly `access_token` 쿠키를 검증한다.
- 프론트 HTTP 요청은 `credentials: "include"` 또는 `withCredentials: true`를 사용한다.
- Socket 연결은 같은 쿠키를 우선 사용한다.
- 보호 API와 Socket 연결은 DB에서 `users.deleted_at`, `users.banned_at`을 다시 확인한다.
- Controller는 검증된 `req.params`, `req.query`, `req.body`, `req.user`, `req.file(s)` 중 필요한 값만 Service에 전달한다.
- Service는 Express `req`, `res` 또는 Socket 객체 전체를 받지 않는다.
- 프론트의 버튼 비활성화는 UX 보조일 뿐이며 서버 검증을 대신하지 않는다.

## 4. Redis 최소 사용 범위

```text
session:{sub}:{sid}
phone:code:{phone}:{purpose}
phone:verified:{phone}:{purpose}
phone:cooldown:{phone}:{purpose}
auction:state:{listingIdx}
```

`auction:state:{listingIdx}`는 Redis Hash로 다음 세 값만 둔다.

```text
currentPrice       20000
highestBidderIdx   3
highestBidIdx      10
```

- `status`, `startPrice`, `endsAt`은 DB에서 읽는다.
- `minNextBid`는 `currentPrice`와 서버 입찰 증가 규칙으로 계산한다.
- `bidCount`와 입찰자 목록은 DB에서 조회한다.
- 상태 key가 없으면 진행 중 경매에 한해 DB의 `current_price`, `winning_bid_idx`로 다시 만든다.
- 종료 또는 삭제가 DB에 확정되면 key를 삭제한다.
- presence, 경매 참여자 목록, 큰 JSON 객체는 Redis에 두지 않는다.

## 5. DB transaction과 부수효과

- 함께 성공해야 하는 핵심 row와 DB 알림·시스템 메시지는 한 transaction에 저장한다.
- 파일 저장처럼 DB 밖에서 일어나는 작업은 실패 시 새 파일 정리 또는 기존 파일 유지 정책을 각 흐름에 적는다.
- Socket emit, Timer 변경, Redis 캐시 정리는 원칙적으로 DB commit 이후 실행한다.
- commit 이후 Socket 전송이 실패해도 DB 결과는 취소하지 않는다. 프론트는 HTTP 재조회로 회복한다.
- 중복 클릭과 재전송은 UNIQUE 제약 또는 현재 상태 조건으로 막는다.

## 6. 거래 완료/취소 고정 부수효과

| 동작 | DB 상태 | 시스템 메시지 | 상대방 알림 |
|---|---|---|---|
| 중고거래 완료 | `transactions.COMPLETED`, `used_posts.SOLD` | `TRADE_COMPLETE` | 판매자에게 `PAYMENT_RECEIVED` |
| 경매 거래 완료 | `transactions.COMPLETED`, 경매는 `FINISHED` 유지 | `TRADE_COMPLETE` | 판매자에게 `PAYMENT_RECEIVED` |
| 송금 요청 취소 | `transactions.CANCELED` | 별도 완료 메시지 없음 | 구매자에게 `PAYMENT_CANCELED` |

경매 종료는 거래 완료가 아니다. 서버는 낙찰 정보만 확정하고, 판매자가 낙찰자를 대상으로 송금 요청을 만들 때 `transactions`가 생성된다.

## 7. 평점 계약

- API 요청·응답과 DB는 정수 `1~10`을 사용한다.
- UI 표시값만 `rating / 2`로 계산해 `0.5~5.0` 별점으로 보여준다.
- 프론트가 5점 UI를 사용하면 제출 직전에 `uiRating * 2`를 정수로 변환한다.
- 평균 평점도 API에서는 10점 기준 원본을 내려주고 UI에서만 2로 나눈다.

## 8. 흐름 문서 확인 방법

각 문서에서 다음 항목을 확인한다.

- `요청 계약`: 프론트가 보내는 값과 중복 요청 방지 방식
- `Frontend`: 버튼, 로딩, 성공/실패 및 Socket 반영
- `Backend 실행 순서`: 인증부터 응답까지 순서가 있는 처리
- `분기`: 권한, 상태, 삭제, 중복, 장애별 결과
- `DB/Redis/Socket`: 읽기·쓰기 주체와 반영 시점
- `무결성 체크`: 다른 계층과 반드시 일치해야 하는 조건
