# 구현 흐름 읽는 법

> 프론트엔드와 백엔드가 같은 명세를 보고 작업하기 위한 구현 체크 문서다.
> API 상세 명세, Socket 이벤트 목록, ERD를 실제 작업 순서로 풀어쓴다.

## 공통 기준

- 보호 HTTP API는 `access_token` 쿠키를 검증한다.
- Socket 연결은 `access_token` 쿠키 우선, 필요 시 handshake auth token을 허용한다.
- 보호 API와 Socket 연결은 DB에서 사용자 `deleted_at`, `banned_at`을 다시 확인한다.
- 요청 데이터는 `req.body`, `req.query`, `req.params`를 검증해 그대로 사용한다. 별도 `req.validated`는 만들지 않는다.
- Socket 현재 화면 상태는 `socket.data.activeChatRoomIdx`, `socket.data.activeAuctionListingIdx`만 사용한다.
- Redis presence, Redis auction participants, `socket.data.joinedRooms`, `phoneVerificationId`는 사용하지 않는다.

## Redis 사용 범위

```text
session:{sub}:{sid}
phone:code:{phone}:{purpose}
phone:verified:{phone}:{purpose}
phone:cooldown:{phone}:{purpose}
phone:reservation:{phone}:{purpose}
auction:state:{listingIdx}
```

`auction:state:{listingIdx}`에는 다음 값만 둔다.

```json
{
  "currentPrice": 20000,
  "minNextBid": 21000,
  "highestBidderIdx": 3,
  "highestBidIdx": 10,
  "updatedAt": "2026-07-31T00:10:00.000Z"
}
```

경매 상태, 시작가, 종료 시간, 입찰자 목록은 DB 기준이다.

## 흐름 문서 형식

- `Frontend 구현 흐름`: 화면, 입력값, 버튼 상태, API/Socket 호출 순서
- `Backend 구현 흐름`: 검증, DB transaction, Redis, Socket emit 순서
- `DB 확인/변경`: 조회 조건과 변경 테이블
- `Redis 확인/변경`: 사용하는 key와 삭제 조건
- `Socket`: join/leave, emit, 수신 후 UI 반영
- `예외 조건`: 프론트에서 code별로 처리할 실패
- `구현 체크리스트`: 작업자가 완료 여부를 확인하는 목록
