# C-01 중고글 등록·수정·삭제

## 요청 계약

| 동작 | 요청 | 주요 입력 |
|---|---|---|
| 등록 | `POST /api/used` | multipart의 상품 필드와 `images[]` |
| 수정 | `PATCH /api/used/:listingIdx` | multipart의 변경 필드와 `images[]` |
| 삭제 | `DELETE /api/used/:listingIdx` | `deleteReason` |

프론트는 `tradeStatus`, `sellerIdx`, `deletedAt`을 보내지 않는다. 서버가 인증 사용자와 현재 상태로 결정한다.

## Frontend 구현 흐름

1. 제목·설명·카테고리·양수 가격·이미지를 검증한다.
2. 제출 중 버튼을 잠그고 `credentials: "include"`로 요청한다.
3. 등록 성공 시 응답 `listingIdx`의 상세로 이동한다.
4. 수정은 서버 상세 응답으로 form을 초기화하고 `SOLD`면 저장을 막는다.
5. 삭제 성공 시 목록 캐시에서 제거하고 상세 링크를 비활성화한다.
6. 오류가 나면 기존 입력을 유지하고 필드 오류와 업로드 오류를 구분한다.

## Backend 등록 순서

1. 인증과 DB의 활성 사용자 상태를 확인한다.
2. body와 파일 개수·MIME·크기를 검증한다.
3. category 존재를 DB에서 확인한다.
4. storage service에 파일을 저장한다.
5. transaction에서 `listings`를 `USED`로, `used_posts`를 `ON_SALE`로, `post_images`를 정렬 순서와 함께 저장한다.
6. commit 후 생성 DTO를 응답한다.
7. rollback이면 새 파일을 best-effort로 정리한다.

## Backend 수정 순서

1. `listings + used_posts`를 조회하고 삭제 글은 `404`로 숨긴다.
2. 판매자 본인인지 확인한다.
3. `trade_status`가 `SOLD`가 아닌지 확인한다.
4. 새 파일을 검증·저장한 뒤 transaction에서 허용 필드와 이미지 row를 교체한다.
5. commit 후 더 이상 참조하지 않는 기존 파일을 정리한다.

## Backend 삭제 순서

1. 판매자 본인 또는 관리자 권한을 확인한다.
2. transaction에서 `listings.deleted_at`, `deleted_by`, `delete_reason`을 저장한다.
3. `favorites`를 삭제한다.
4. 기존 `chat_rooms`, `chat_messages`, `transactions`, `reviews`는 보존한다.
5. commit 후 성공 응답한다. Redis와 Socket 변경은 없다.

## 분기

| 조건 | 결과 |
|---|---|
| 미인증/비활성 | `401` / `403` |
| 잘못된 입력·파일 | `400 VALIDATION_ERROR` / `UPLOAD_FAILED` |
| 판매자 아님 | `403 FORBIDDEN` |
| 없음/삭제됨 | `404 NOT_FOUND` |
| 판매 완료 수정 | `409 CONFLICT` |
