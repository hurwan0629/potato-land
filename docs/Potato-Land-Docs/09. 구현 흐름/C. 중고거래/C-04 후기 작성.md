# C-04 후기 작성

## 요청 계약

`POST /api/reviews`

```json
{
  "transactionIdx": 1,
  "revieweeIdx": 2,
  "rating": 9,
  "content": "좋은 거래였습니다.",
  "strengthTagIdxs": [1, 2],
  "weaknessTagIdxs": []
}
```

`rating`은 API와 DB에서 정수 `1~10`이다.

## Frontend 흐름

1. 거래내역의 `canWriteReview=true`인 항목만 작성 버튼을 표시한다.
2. 0.5~5점 UI 값을 제출할 때 `uiRating * 2`로 변환한다.
3. 제출 중 버튼을 잠근다.
4. 성공하면 작성 버튼을 제거하고 후기·프로필 평균을 재조회한다.
5. 응답의 rating과 평균은 화면에서만 `/ 2`해 표시한다.
6. form 취소는 화면만 닫으며 거래 상태를 변경하지 않는다.

## Backend 실행 순서

1. 인증·활성 사용자와 body 형식을 검증한다.
2. rating이 정수 `1~10`, content가 최대 50자인지 확인한다.
3. 장점/아쉬운 점 태그가 각각 최대 3개이고 활성 태그의 종류와 요청 배열이 일치하는지 확인한다.
4. transaction을 시작하고 대상 거래를 조회한다.
5. 거래가 `COMPLETED`인지 확인한다.
6. 요청자가 seller 또는 buyer인지 확인한다.
7. `revieweeIdx`가 정확히 상대 참여자인지 서버에서 계산해 확인한다.
8. `(transaction_idx, reviewer_idx)`의 기존 후기를 확인한다.
9. `reviews`, `review_tag_selections`와 상대방의 `NEW_REVIEW` 알림을 저장한다.
10. commit 후 상대 개인 room에 알림과 절대 unread count를 전송한다.

DB UNIQUE `(transaction_idx, reviewer_idx)`와 CHECK `rating BETWEEN 1 AND 10`, `reviewer_idx <> reviewee_idx`가 서비스 검증의 마지막 방어선이다.

## 분기

| 조건 | 결과 |
|---|---|
| rating 정수 1~10 아님 | `400 VALIDATION_ERROR` |
| 거래 참여자 아님/상대방 불일치 | `403 FORBIDDEN` |
| 거래 미완료 | `409 CONFLICT` |
| 이미 작성 | `409 CONFLICT` |

## 저장소와 동기화

- DB: `transactions`, `reviews`, `review_tags`, `review_tag_selections`, `notifications`, 평균은 조회 시 aggregate
- Redis: 후기나 평균 평점을 캐시하지 않는다.
- Socket: commit된 `NEW_REVIEW` 알림만 전달한다.

## 무결성 체크

- [ ] API/DB rating 1~10 정수
- [ ] UI에서만 2로 나눔
- [ ] 양방향 후기와 사용자당 거래별 1회
- [ ] 상대방을 서버에서 계산·검증
- [ ] 후기 내용 50자 및 종류별 태그 최대 3개 검증
- [ ] commit 전 알림 emit 금지
