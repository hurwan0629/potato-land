# C-03 송금 요청·완료·취소

## 요청 계약

| 동작 | 요청 | 수행자 |
|---|---|---|
| 거래/송금 요청 생성 | `POST /api/transactions/payment-requests` | 판매자 |
| 거래 조회 | `GET /api/transactions/:transactionIdx` | 참여자 |
| 송금 완료 | `PATCH /api/transactions/:transactionIdx/complete` | 구매자/낙찰자 |
| 요청 취소 | `PATCH /api/transactions/:transactionIdx/cancel` | 판매자 |

생성 body는 `listingIdx`, `buyerIdx`, `amount`, 선택적 `message`를 사용한다. 프론트가 `sellerIdx`나 `status`를 보내지 않는다.

## Frontend 흐름

1. 중고글 판매자는 해당 구매 희망자 채팅에서 송금 요청을 만든다.
2. 경매 판매자는 종료 상세의 낙찰자 정산 버튼에서 요청을 만든다.
3. 생성 요청 중 버튼을 잠근다.
4. 구매자는 `PAYMENT_REQUEST` 메시지 또는 거래내역에서 송금 화면으로 이동한다.
5. 송금 화면의 단순 뒤로가기는 서버의 취소 API를 호출하지 않는다.
6. 완료/취소 응답이나 Socket 메시지를 받으면 거래 상세를 다시 조회해 UI를 확정한다.

## 송금 요청 생성 순서

1. 인증·활성 사용자와 body를 검증한다.
2. DB에서 listing, 판매자, 구매자와 타입별 상태를 조회한다.
3. 요청자가 판매자이고 buyer가 활성 상태이며 서로 다른 사용자인지 확인한다.
4. 중고글은 거래 가능한 상태와 구매 희망자 채팅 관계를 확인한다.
5. 경매는 `FINISHED`, buyer가 DB 낙찰자, amount가 최종 낙찰가인지 확인한다.
6. 동일 listing에 `REQUESTED` 또는 `COMPLETED` 거래가 없는지 확인한다. DB 부분 UNIQUE 인덱스가 최종 방어선이다.
7. 일반/정산 채팅방을 조회하고 경매 정산 방은 필요하면 생성한다.
8. 한 transaction에서 `transactions.REQUESTED`, `PAYMENT_REQUEST` 메시지, 구매자 `PAYMENT_REQUESTED` 알림을 저장한다.
9. commit 후 새 방이면 `chat:room:new`, 채팅방에 `chat:message:new`, 개인 room에 알림·unread count를 전송한다.

## 송금 완료 순서

1. 거래 row를 transaction에서 잠근다.
2. 요청자가 buyer이고 양 참여자가 활성 상태인지 확인한다.
3. 현재 상태가 정확히 `REQUESTED`인지 확인한다.
4. `transactions.status = COMPLETED`, `completed_at = now`를 저장한다.
5. 중고거래라면 `used_posts.trade_status = SOLD`로 변경한다. 경매는 `FINISHED`를 유지한다.
6. 같은 transaction에서 `sender_idx=NULL`인 `TRADE_COMPLETE` 시스템 메시지를 저장한다.
7. 판매자에게 `PAYMENT_RECEIVED` 알림을 저장한다.
8. commit 후 `chat:message:new`, 판매자 `notification:new`, 양측 `chat:room:updated`를 전송한다.

## 송금 요청 취소 순서

1. 거래 row를 잠그고 요청자가 seller인지 확인한다.
2. 현재 상태가 정확히 `REQUESTED`인지 확인한다.
3. `transactions.status = CANCELED`, `updated_at = now`로 변경한다.
4. 구매자에게 `PAYMENT_CANCELED` 알림을 저장한다.
5. 별도의 `canceled_at`, `cancel_reason`과 `TRADE_COMPLETE` 메시지는 만들지 않는다.
6. commit 후 알림과 채팅방 갱신 이벤트를 전송한다.

## 동시 요청과 재전송

- 완료와 취소가 동시에 오면 row lock 뒤 먼저 `REQUESTED`를 변경한 요청만 성공한다.
- 이미 `COMPLETED` 또는 `CANCELED`이면 상태를 다시 바꾸지 않고 `409 CONFLICT`를 반환한다.
- 활성 요청 중복은 서비스 조회와 DB 부분 UNIQUE 제약으로 함께 막는 것을 권장한다.

## 저장소 책임

- DB: `transactions`, `chat_rooms`, `chat_messages`, `notifications`, 완료 시 `used_posts`
- Redis: 사용하지 않는다.
- Socket: DB commit된 메시지·알림·목록 갱신만 전달한다.
