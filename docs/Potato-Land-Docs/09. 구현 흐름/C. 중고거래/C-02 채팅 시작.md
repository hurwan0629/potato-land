# C-02 일반 채팅·경매 정산 채팅 시작

## 목적

일반 상품 문의 채팅과 종료 경매의 판매자·낙찰자 정산 채팅을 분리해 권한을 판단한다.

## 일반 채팅 요청

`POST /api/chats`

```json
{
  "listingIdx": 1
}
```

구매 희망자가 상세 화면에서 호출한다.

## 일반 채팅 Backend 순서

1. 인증·활성 사용자와 `listingIdx`를 검증한다.
2. DB에서 listing, 판매자, 타입별 상태를 조회한다.
3. 삭제 글, 비활성 판매자, 판매자 본인 요청을 차단한다.
4. 중고글은 `ON_SALE` 또는 정책상 허용한 상태인지 확인한다.
5. 경매는 `ON_GOING`이고 종료 전일 때만 허용한다.
6. `(listing_idx, seller_idx, buyer_idx)` 기준 기존 방을 조회한다.
7. 있으면 그대로 반환하고 없으면 transaction으로 `chat_rooms`를 만든다.
8. 새 방일 때만 상대 개인 room에 `chat:room:new`를 전송한다.

같은 요청이 재전송돼도 UNIQUE 제약과 재조회로 하나의 방만 반환한다.

## 종료 경매 정산 채팅

일반 `POST /api/chats`로 만들지 않는다. 판매자가 `POST /api/transactions/payment-requests`를 호출할 때 서버가 다음 조건으로 생성 또는 재사용한다.

1. 경매가 `FINISHED`이고 삭제되지 않았는지 확인한다.
2. 요청자가 판매자인지 확인한다.
3. `buyerIdx`가 DB `winning_bid_idx`의 입찰자인지 확인한다.
4. `amount`가 DB 최종 낙찰가와 같은지 확인한다.
5. 판매자와 낙찰자가 활성 사용자인지 확인한다.
6. 정산 채팅방을 조회해 없으면 생성한다.
7. 같은 transaction에서 `REQUESTED` 거래와 `PAYMENT_REQUEST` 메시지를 만든다.

이 방은 종료 경매의 일반 채팅 제한에서 예외다. 거래가 `REQUESTED`인 동안 판매자와 낙찰자는 메시지를 보낼 수 있다. 완료·취소 뒤에도 과거 메시지는 조회 가능하며, 쓰기 가능 여부는 채팅 정책에서 계산한다.

## Frontend 처리

- 상세 응답의 `canChat`으로 일반 문의 버튼을 제어한다.
- 판매자는 종료 경매의 `canCreateSettlement`으로 별도 거래 생성 버튼을 제어한다.
- 채팅 생성 성공 시 `chatRoomIdx`로 이동한다.
- 종료 경매 낙찰자는 일반 채팅 버튼이 아니라 거래내역에 생성된 정산 방으로 진입한다.

## 분기

| 조건 | 결과 |
|---|---|
| 판매자 본인의 일반 채팅 | `403 FORBIDDEN` |
| 삭제 글/경매 | `404 NOT_FOUND` |
| 종료 경매 일반 채팅 | `409 AUCTION_CLOSED` |
| 비활성 참여자 | `409 INACTIVE_USER` |
| 낙찰자 아닌 buyer로 정산 생성 | `403 FORBIDDEN` |
| 동일 활성 송금 요청 존재 | `409 CONFLICT` |

## 저장소와 동기화

- DB: `listings`, 타입별 게시글, `users`, `chat_rooms`; 정산 생성은 `transactions`, `chat_messages`, `notifications` 추가
- Redis: 사용하지 않는다.
- Socket: 새 방과 commit된 결제 요청 메시지만 전송한다.
