# A-01 전화번호 인증

## 요청 계약

- 발송: `POST /api/auth/phone/send` `{ phone, purpose }`
- 검증: `POST /api/auth/phone/verify` `{ phone, purpose, phoneVerificationId, code }`
- 상태: `GET /api/auth/phone/status?phone=&purpose=&phoneVerificationId=`
- purpose: `SIGNUP`, `FIND_ID`, `RESET_PASSWORD`, `CHANGE_PHONE`

## Frontend 순서

1. 전화번호를 정규화하고 화면 목적에 맞는 고정 purpose를 보낸다.
2. 발송 응답의 `phoneVerificationId`를 화면 상태에 저장하고 30초 동안 재발송 버튼을 잠근다.
3. 사용자가 입력한 code를 같은 phone/purpose/phoneVerificationId로 검증한다.
4. 성공하면 같은 식별자를 회원가입·아이디 찾기·비밀번호 재설정·전화번호 변경 API에 보낸다.
5. 전화번호나 purpose가 바뀌면 기존 화면 인증 상태를 폐기한다.

## Backend 발송 순서

1. phone 형식과 허용 purpose를 검증한다.
2. `phone:cooldown:{phone}:{purpose}`가 있으면 `429`로 차단한다.
3. purpose별 DB 사전 조건을 확인한다.
   - `SIGNUP`, `CHANGE_PHONE`: 이미 사용 중인 번호인지 확인
   - `FIND_ID`, `RESET_PASSWORD`: 상세한 가입 여부를 노출하지 않는 응답 정책 적용
4. 6자리 code와 무작위 `phoneVerificationId`를 만들고 SMS provider를 호출한다.
5. 발송 성공 후에만 식별자를 포함한 code key TTL 3분, cooldown key TTL 30초를 저장하고 식별자를 응답한다.
6. 로그에는 원문 code를 남기지 않는다.

## Backend 검증 순서

1. phone/purpose/phoneVerificationId/code 형식을 검증한다.
2. `phone:code:{phone}:{purpose}`를 읽는다.
3. 저장된 phoneVerificationId가 요청과 같은지 확인하고 안전한 방식으로 code를 검증한다.
4. 성공하면 code key를 삭제하고 같은 식별자를 포함한 `phone:verified:{phone}:{purpose}`를 TTL 10분으로 저장한다.
5. SIGNUP도 별도 reservation 없이 verified key만 사용한다.

## 실패와 Redis

| 조건 | 결과 |
|---|---|
| cooldown 중 | `429 TOO_MANY_REQUESTS` |
| code 없음/만료/불일치 | `400 VERIFICATION_FAILED` |
| SMS provider 실패 | code/cooldown 미생성, `502` 또는 통일된 외부 서비스 오류 |
| Redis 장애 | 인증 상태를 보장할 수 없으므로 요청 차단 |

## 무결성 체크

- [ ] purpose가 key와 후속 API까지 동일
- [ ] 발송 성공 뒤 key 저장
- [ ] 검증 성공 시 code 소비
- [ ] verified TTL 10분
- [ ] 후속 API에서 phoneVerificationId 일치 확인 후 verified key 소비
