# A-03 로그인·재발급·로그아웃

## 요청 계약

- `POST /api/auth/login` `{ loginId, password }`
- `POST /api/auth/refresh` body 없음, refresh cookie 사용
- `POST /api/auth/refresh/logout` body 없음, refresh cookie 사용

모든 요청은 `credentials: "include"`를 사용한다.

## Frontend 공통 흐름

- 로그인 성공 후 토큰 문자열을 저장하지 않고 사용자 정보를 다시 조회한다.
- 보호 API의 401은 하나의 refresh 요청으로 묶고 원래 요청은 한 번만 재시도한다.
- refresh 실패 또는 로그아웃 시 Socket과 사용자 캐시를 정리한다.

## Backend 처리 흐름

아래 로그인·재발급·로그아웃 순서가 각각의 서버 실행 경계다.

## 로그인 순서

1. 입력 형식을 검증하고 DB에서 loginId 사용자를 조회한다.
2. password hash를 비교한다. 존재 여부와 비밀번호 오류는 같은 `INVALID_CREDENTIALS`로 응답한다.
3. `deleted_at`, `banned_at`을 확인한다.
4. 새 `sid`, access jti, refresh jti를 만든다.
5. Redis `session:{sub}:{sid}`에 현재 refresh jti를 TTL 7일로 저장한다.
6. Redis 저장 성공 후 access(15분)·refresh(7일) 쿠키를 설정해 응답한다.
7. Redis 저장 실패 시 쿠키를 발급하지 않는다.

## 재발급 순서

1. refresh cookie JWT 서명·만료·`type=refresh`를 검증한다.
2. Redis session을 읽고 `currentRefreshJti`와 token jti를 비교한다.
3. DB에서 사용자의 현재 활성 상태와 role을 다시 조회한다.
4. 일치하면 새 access/refresh jti를 만들고 Redis jti와 TTL을 rotation한다.
5. 새 쿠키를 설정한다.
6. jti 불일치는 재사용으로 보고 해당 session key와 쿠키를 폐기한다.

재발급은 Access Token만 연장하지 않고 Refresh Token Rotation까지 함께 수행한다. 따라서 사용자가 계속 보호 API를 호출한다면 access 만료 후 첫 요청을 계기로 대략 15분 간격으로 두 쿠키가 갱신될 수 있다. 요청이 없는 동안 주기적으로 호출하지는 않는다.

같은 만료 access 요청이 동시에 여러 번 refresh를 호출하지 않도록 프론트는 하나의 refresh Promise를 공유하고 실패했던 요청을 한 번씩만 재시도한다.

## 로그아웃 순서

1. 가능한 경우 refresh cookie의 sub/sid를 검증한다.
2. 해당 `session:{sub}:{sid}`만 삭제한다.
3. 검증 실패나 key 없음과 관계없이 두 쿠키를 정확한 Path로 만료한다.
4. 프론트는 사용자 캐시와 Socket 연결을 종료한다.

## 무결성 체크

- [ ] access claim에 role, refresh에는 role 없음
- [ ] Redis session 저장 성공 후 쿠키 발급
- [ ] refresh rotation jti 비교
- [ ] 재발급 시 DB 활성 상태·role 재조회
- [ ] 로그아웃 idempotent 처리
- [ ] refresh cookie Path `/api/auth/refresh`
